## 1. 一句话

**Nucleus** 是一个「说一句话 → 得到可运行、可交互、可迭代、可带走」的网页应用生成工作台。它的核心不是聊天框，而是**把 Agent 的生成过程做成一条可观察、可中断、可回滚的流水线**：左边是计划与文件流，右边是立刻能点的应用，中间每一次改动都落到版本上。

对比 Atoms / v0 / Bolt 这类产品，我不追求「生成得更花」，而是集中在三件它们做得不够好的事：

1. **过程可见**：模型在想什么、要建哪些文件、每个文件写到第几行，全部实时可见，而不是一个转圈的 spinner；
2. **产物跑起来才算数**：生成完自动挂进沙箱；应用内部报错会被桥接回宿主，变成「一键让 Agent 修」的入口；
3. **产物可带走**：任意版本可回滚、可导出成**双击就能打开的 ZIP**、可生成免登录的分享链接。

### 1.1 四个环节都在（Atoms 对齐自查）

| Atoms 环节 | 本项目的实现 | 在哪看 |
| --- | --- | --- |
| ① 对话即入口，背后是**任务简报** | `<plan>` 协议事件 → 方案卡（应用名 / 简介 / 技术栈 / 步骤 / 文件清单），**出现在任何代码之前** | 工作台左栏顶部 |
| ② **每一步工作都可见** | 阶段药丸（拆解需求 → 编写代码 → 静态自检）+ 逐文件流式写入（真实路径、真实行数）+ 检查徽章 | 工作台左栏 |
| ③ 生成结果是**可交互版本** | 沙箱 iframe 里真实可点，三档视口；应用内报错实时浮条 | 工作台右栏 |
| ④ 追加修改是**增量且可回滚** | 只重写变化的文件；不可变版本快照；回滚本身也生成新版本 | 版本面板 |

四个环节缺任何一个，产品就退化成「能生成代码的聊天框」。这张表可以直接对着线上链接逐条验。

## 3. 实现思路

### 3.1 核心命题：让「生成」变成一条可消费的事件流

普通实现是：等模型吐完 3 万字符 HTML → `innerHTML` 塞进 iframe。代价是用户干等 40 秒、中途无法介入、失败只能重来、产物只能整块替换。

我的做法是**定义一个中间协议**，让 Agent 的输出天然可增量消费：

```
<note>我来做一个记账应用，先搭结构</note>
<plan>{"name":"记账本","files":[{"path":"index.html","purpose":"页面骨架"}],"steps":["布局","逻辑"]}</plan>
<file path="index.html">
<!doctype html> ...
</file>
```

这份格式我叫它 **NWF（Nucleus Wire Format）**。它不是「为了炫技自己发明语法」，而是解决四个具体问题的**最小代价方案**：

| 问题 | NWF 的回答 |
| --- | --- |
| 流式解析要能任意位置断流 | 文件内容区**不解析标签、不转义**，只有 `</file>` 是边界；半截标签退化为正文（`isPossibleTagPrefix`） |
| 分块边界会切碎标签 | 解析器是**字符级状态机**，逐字符喂入与整体喂入产出完全一致的事件序列（UT-PROTO-02/03 用随机分块断言） |
| 解析器绝不能崩 | 所有异常路径降级为 `warning` 事件，永不 throw——流断了用户也还能看到已完成的部分 |
| 前端、后端、测试要有共同语言 | 统一成 `AgentEvent`（11 种）写在 `shared/types.ts`，SSE 传输、前端 reducer、测试断言**共用同一份定义** |

这条事件流是整条流水线的主动脉：`stage → note → plan → file_start → file_delta* → file_end → (delete)* → check* → done`。UI 只是它的渲染器，测试只是它的断言器。

**一次请求的完整时序**（含每个事件对应 Atoms 的哪个环节）见 [04 §2.3](04-技术设计文档.md)。

### 3.2 双引擎：环境没有模型 Key 时，产品不能假装在工作

这是本次笔试最实际的约束：**没有可用的模型 Key**。三条路：

- A. 只做云端，要求评审自己填 Key → 大概率打不开就关掉，等于没交付；
- B. 假装调了模型，实际返回写死的 HTML → 一旦被点破，信任归零；
- C. **双引擎**：做一个真的本地编译器保证「打开即用」，同时保留完整的云端链路，配 Key 即切换。

我选 C，并且给 C 加了两条纪律：**绝不静默降级**（UI 常驻显示当前引擎，设置页可显式切换、可测试连接）、**本地引擎必须是真编译器而不是模板替换**。

「真编译器」的判定标准写进了测试 UT-COMP-10：

```
同一句需求，只改主色 → 产物 CSS 变量必须不同
改应用名 → 标题、storage key、导出文件名必须跟着变
改货币 → 金额格式化必须从 ¥ 变成 $ / €
```

本地编译器分三段：**意图分类**（加权词表 + 稳定 tie-break，避免同分随机）→ **槽位抽取**（名称/主色/主题/货币/字段）→ **配方发射**（7 个 archetype：记账、待办、笔记、番茄钟、看板、计算器、落地页）。同输入必须字节一致，才能做黄金测试。

云端引擎走 OpenAI 兼容 SSE，做了三件容易被忽略的事：**SSRF 校验**（拒绝内网/本机地址，否则一个填写 Base URL 的输入框就是内网探测器）、**首字节 30s / 空闲 60s 超时**（否则用户会盯着一个永不返回的请求）、**错误码归一**（401 → `llm_auth`，让前端能提示「Key 无效」而不是「未知错误」）。

### 3.3 预览沙箱：让生成的应用「真的能用」

生成一个 HTML 容易，让它**在里面点得动、数据存得住、出错了还能被外面知道**才是难点。三个设计：

1. **单文件组装**：把多文件项目的 CSS/JS 内联回 `index.html`（保持原有位置），产出单个 `srcdoc`。这样不需要起多个端口、不需要处理相对路径，产物天然可移植。
2. **沙箱策略只给必要权限**：`allow-scripts allow-forms allow-modals allow-popups allow-downloads`，**不给** `allow-same-origin`。代价是 `localStorage` 在沙箱里会抛 `SecurityError`——所以注入了一层**内存版 storage shim**，并把写入同步回宿主，宿主再次挂载时回灌种子。这样「刷新预览，刚才记的账还在」成立，同时没有把宿主源暴露给不可信代码。
3. **错误桥**：在 iframe 内捕获 `error` / `unhandledrejection` / `console.error`，用 `postMessage({__nucleus:1})` 回传宿主，宿主聚合去重后弹一条浮条：「应用报错了 → 让 Agent 修」。点击后自动把**错误信息 + 堆栈 + 当前代码**打包成修复指令，走正常的迭代链路——用户不需要会描述 bug。

### 3.4 持久化与版本：够用、可解释、可迁移

存储用**单文件 JSON + 原子写**（写 tmp → `rename`），配一个串行写队列防并发撕裂。否决 SQLite 的理由很直接：这是个要能被打包、被 `git clone` 后立刻跑起来的 Demo，引入原生模块编译会显著提高「跑不起来」的概率，而收益（并发、索引）在单用户场景为零。

版本模型是**整份文件快照**而非增量 diff。理由：一个生成的应用总共 20–60 KB，快照的存储成本可以忽略，换来的是回滚变成 O(1) 的指针切换，且永不出现「diff 链断裂导致版本无法还原」。回滚本身**也生成新版本**，历史不可变——这是给用户的安全感。

几处细节：生成过程中**不落盘**（只在 `done` 时提交，避免半成品污染历史）、版本上限 30（保留首版 + 最近 5 版）、所有路径过 `sanitizePath` 白名单（`..`、绝对路径、反斜杠一律拒绝）。

### 3.5 零依赖：能自研的就自研

运行时依赖只有 `react` / `react-dom`，服务端只用 Node 内置模块。四样东西自己写了：

- **hash 路由**（~40 行）：`/` `/studio/:id` `/p/:slug` `/settings`，无需服务端配合；
- **语法高亮**（~80 行）：先切词再 escape（顺序反了就是 XSS），覆盖 HTML/CSS/JS/JSON；
- **ZIP 打包**（~60 行）：store 模式 + CRC32，够用且能在 200 行内看懂、被测试覆盖；
- **文本 diff**（~60 行）：LCS + 上限退化，用于版本对比。

不是反依赖，而是这四件事要么太小、要么对安全太敏感（高亮的 escape 顺序），自己写反而更可控。

### 3.6 设计微调：不是所有修改都值得走一次模型

上线后最常被要求的两件事是「换个主色」和「圆角小一点」。这类需求有两个特征：**目标是确定的**（用户已经知道自己要什么），**改动是局部的**（只动 CSS 变量）。让模型来做，要付出 1–2 秒等待、不可复现的结果，还会在版本历史里留下一个"只改了一行 CSS"的版本——三条都是负收益。

所以这里做了一个明确的切分：**语义修改走 Agent，视觉参数走微调面板**。

- 生成物统一用 `--accent / --accent-soft / --accent-ink / --radius` 表达视觉（本地引擎的 7 个原型都遵守这个约定）；
- 面板把「主色 / 圆角」翻译成一组变量，宿主用 `postMessage` 写进沙箱 `documentElement` 的内联样式。**iframe 不重载**，所以应用里刚填的表单、列表状态、滚动位置全部保留；
- 变量派生（浅底色、按钮文字色）写在 `shared/theme.ts`，**服务端注入与前端实时推送共用同一份算法**——否则会出现"调色时一个颜色、刷新后另一个颜色"这种最难查的不一致；
- 持久化：`PATCH /api/projects/:id { tweak }`，进入项目而不是版本（视觉参数不是一次"代码变更"）。刷新、分享页、导出 ZIP 三处都由服务端注入同一段 `<style data-nucleus="tweak">`，所以**别人看到的和你看到的一样、下载下来也一样**；
- 诚实的边界：如果某个应用没有声明设计令牌（比如云端模型生成的自定义 CSS），自检里的「可用设计令牌」会标红，面板会提示"只能调圆角"，而不是假装生效。

这条能力还顺手解释了一个常见误区：**"AI 生成的应用"不等于"什么都必须由 AI 改"**。把确定性的事情交还给确定性代码，模型预算才能花在真正需要理解意图的地方。

## 4. 关键取舍一览



| # | 决策 | 被否方案 | 为什么 |
| --- | --- | --- | --- |
| 1 | 自研 NWF 流式协议 | 让模型直接吐完整 HTML；或 JSON + function calling | 完整 HTML 无法增量渲染、无法中途纠正；JSON 需要转义且断流即废，token 成本更高 |
| 2 | 双引擎（本地编译器 + 云端） | 只做云端；或写死演示数据 | 无 Key 也要能打开即用；但绝不假装调用模型，引擎状态全程可见 |
| 3 | 本地也是「编译器」 | 一句需求 → 一张固定模板 | 模板会被一眼看穿；槽位必须真实改变产物（有测试守着） |
| 4 | 单文件 JSON + 原子写 | SQLite / Postgres | 零编译依赖、可随仓库搬运；单用户场景并发收益为零 |
| 5 | 整份快照做版本 | 增量 diff 存储 | 20–60 KB/版，成本可忽略；回滚 O(1)，无 diff 链断裂风险 |
| 6 | `srcdoc` + 内联组装 | 多端口静态服务 / 每个项目独立构建 | 免端口、免路径、产物可直接导出为单文件；代价是需自己做 CSP 与 storage shim |
| 7 | 沙箱不给 `allow-same-origin` | 给全权限换省事 | 生成代码不可信；宁可自己做 storage shim，也不把宿主源暴露出去 |
| 8 | 前端手写 CSS 变量主题 | Tailwind / 组件库 | 免构建插件与版本漂移；设计令牌集中，换肤只改一处 |
| 9 | 匿名 `visitorId`，不做注册 | 账号体系 | 题面明确「无需注册」；访客维度已足够做「我的项目」 |
| 10 | 自研 4 个小件 | 引 4 个库 | 每个都 <100 行、且高亮的 escape 顺序是安全要害，自己写更可控 |
| 11 | 视觉参数（主色/圆角）走微调面板，不走模型 | 一律发一次生成请求 | 确定性的变换交给确定性代码：毫秒级、可复现、不污染版本历史；代价是依赖"应用用设计令牌"的约定，所以自检里如实标注 |
| 12 | 微调实时用 `postMessage` 推变量，不重载 iframe | 重新组装 srcdoc 刷新预览 | 重载会清空应用内状态（填了一半的表单没了），"调个颜色"不该有这个代价 |

**明确不做的取舍**：不做多人协作、不做自定义域名发布、不做移动端 App、不做计费。原因见 §5。

### 4.1 与常见参考方案的差异（重点）

笔试这类任务通常有一份"标准做法"：Next.js 全栈 + Vercel AI SDK + Supabase + CDN React/Babel 预览。我没有照抄——**每一项差异背后都有一个那份方案没回答的问题**：

| 议题 | 参考方案常见选择 | 本项目的选择 | 理由（含代价） |
| --- | --- | --- | --- |
| 全栈框架 | Next.js App Router | React + Vite + `node:http` | Demo 无 SSR/SEO 需求；`node:http` 零框架、启动 <100ms。代价：公开页 SEO 需迁回框架 |
| 流式客户端 | Vercel AI SDK `useChat` | 自研 SSE + reducer（~120 行） | `useChat` 的模型是「消息 + 工具调用」，本项目要消费的是**文件级增量流**，套用反而要拆掉它的抽象。代价：自己承担取消与断线逻辑 |
| 生成协议 | JSON / XML 标签 | 自定义 NWF 行协议 | JSON 不闭合即无法解析；NWF 让内容区完全不解析、只认边界标签。代价：模型要学非标格式，靠漂移纠正兜底 |
| 生成物 | 单文件 React + Babel standalone | 原生 HTML/CSS/JS 三件套 | Babel standalone 约 2.7MB 且每次预览都重新编译，产物还依赖 CDN 可用性。代价：放弃 JSX 与组件生态 |
| 沙箱 | `iframe srcdoc` + `allow-scripts` | 同上，**额外**处理了 storage 与同源 | 不给 `allow-same-origin` 后原生 storage 抛 `SecurityError`，"刷新数据还在"其实不成立——这一点参考方案没覆盖 |
| 云端沙箱 | E2B / WebContainers | 纯前端沙箱 | 鉴权、配额、冷启动、预览 URL 会吃掉大半时间。代价：不支持多文件构建型产物与真实终端命令 |
| 持久化 | Supabase | 单文件 JSON + 原子写 | 零外部依赖、免账号。代价：单进程，不能多实例 |
| 多角色 | Emma/Alex/Mike 切三张卡 | 阶段化输出（简报→编写→验收） | 一次调用切三角色只是文案，成本/延迟/一致性都不变；预算应花在活动卡片的真实信息量上。代价：少了"团队接力"的观感 |
| Race Mode | 并行多模型 | 切引擎/模型名 + 版本对比 | 并行要额外预算与仲裁逻辑。代价：没有并排赛马的观感 |

完整版（含每条代价的展开）见 [03 §2.1](03-技术架构文档.md)。**这张差异表本身就是交付物的一部分**——它证明我做的是取舍，而不是没想过那些方案。

## 5. 交付顺序：每一步结束都可演示

提交历史（15 个提交）就是**依赖顺序**，不是时间线（提交是批量打的，时间戳不可信）。这个顺序本身就是一条工程决策：

```
①  需求 → PRD → 架构 → 设计（先想清楚再写码）
②  shared/types.ts          全系统唯一契约先定死
③  protocol.ts              增量状态机（协议先于引擎）
④  composer.ts              本地编译器（先有一个一定能跑的引擎）
⑤  llm.ts / runner.ts       云端引擎与双引擎编排
⑥  assemble.ts              沙箱组装、错误桥、存储回灌
⑦  store.ts                 原子写、版本快照、回滚
⑧  zip.ts                   自研 ZIP 与导出
⑨  server/index.ts          路由、SSE、分享
⑩  src/                     React 工作台（对话流/预览/代码/版本）
⑪  tests/                   147 条单元集成 + 12 步 E2E
⑫  docs/ + README + 截图     交付说明、界面截图、线上链接
```

三条经验：

1. **契约先于实现**：`shared/types.ts` 写在所有代码之前，因为它定义的是「后端产出、SSE 传输、前端消费、测试断言」四方共用的 `AgentEvent`。先定契约，后面的实现都是填空。
2. **协议先于引擎**：先把 NWF 的状态机和它的 22 条边界用例写完，再写引擎。于是引擎只要「吐出协议文本」这一件事，本地与云端共用同一条链路。
3. **界面最后写**：写界面时事件序列已经是确定的，UI 只是渲染器——所以最终能写出 147 条断言同一份契约的测试，而不是对着界面截图写断言。

## 8. 如果继续投入，我会怎么排优先级

排序依据是「**对用户价值的边际提升 / 实现成本**」，不是「技术上有趣」。

**已完成（原 P0 清单，交付前补齐）**

1. ✅ **生成中途打断并保留** —— 「停止」不再丢弃：连接不断开，服务端中断引擎后把**正常闭合**的文件提交为新版本，写了一半的回退到旧版（`done{partial,kept}` 回传确认）。
2. ✅ **上下文预算优化** —— 不再"超预算整份丢弃"（那会让模型以为文件不存在而重建它）：改为相关度排序 + 单文件截断 + manifest 标注哪些没给全。
3. ✅ **健康度自检面板** —— 静态自检结论常驻在预览工具栏，点开看每一项判定与详情。

**P0（半天内，直接补强现有闭环）**

1. **生成中途真正打断**（区别于"停止并保留"）：现在停止会等当前文件写完，下一步支持"立刻停、连当前文件都不要"。
2. **上下文摘要**：现在是"相关度排序 + 截断"，文件多起来后仍要配合"摘要 + 相关文件检索"，让长会话（>10 轮）不退化。
3. **错误重试入口**：错误条已有"重新生成"按钮，下一步让它带上原失败的那条指令，而不是重新发送输入框里的内容。

**P1（1–2 天，扩大能力边界）**

4. **多页面 + 路由**：当前配方都是单页。支持 `pages/` 目录与前端路由，是「玩具」到「真项目」的分水岭。
5. **真云模型 A/B**：同一个 prompt 并行跑本地编译器与云端，把两份结果并排给用户选（成本可控版 Race Mode），并把选择结果作为偏好数据沉淀。
6. **图片/图标资源管线**：现在只允许内联 SVG / emoji。加一个受控的资源目录，避免生成的应用全是色块。

**P2（1 周，产品化）**

7. **模板市场与 fork**：任何生成结果可一键发布为模板，形成供给侧循环。
8. **数据库型应用**：把「localStorage 单机」升级为可选的后端表（当前架构在 `Store` 层已预留抽象）。
9. **团队空间与权限**：只有到这一步才需要账号体系。

**明确不排期**：计费、自建域名、原生 App。它们不改变「生成体验」本身。
