# 04 · 技术设计文档

本文只写"怎么做"，不重复"做什么"。分六个部分：生成协议、Agent 编排、生成链路（提供方目录 / 闸门 / 故障转移 / 修复轮）、预览组装与沙箱、持久化与版本、前端状态机。

## 1. 生成协议（Nucleus Wire Format, NWF）

### 1.1 为什么不用纯 JSON

最直觉的方案是让模型输出 `{"files":[{"path":"...","content":"..."}]}`。三个问题：

1. **流式体验差**：JSON 不闭合就无法解析，用户在整个生成期间只能看一个 loading；
2. **转义易错**：`content` 里的双引号、反引号、换行要转义，模型经常漏掉一个 `\`，整份输出报废；
3. **无法逐文件上报进度**：拿不到"正在写 styles.css"这种中间态。

所以采用**基于定界符的行文本协议**：内容区是原始文本（不转义），边界靠标签，解析器是增量状态机，任意位置断流都能恢复。

### 1.2 语法

```
<note>自由文本，会作为 Agent 的口播显示在对话流</note>
<plan>{ "name": string, "summary": string, "stack": string,
        "steps": string[], "files": [{"path": string, "purpose": string}] }</plan>
<file path="index.html">
（原始文件内容，可含任意字符）
</file>
<delete path="old.js"/>
```

规则：

- 标签名大小写不敏感；属性值允许单/双引号；
- `<file>` 内容的首尾各去掉一个换行（模型习惯在标签后换行）；
- 模型若把内容包进 ```` ```html ... ``` ````，解析器在 `file_end` 时剥离围栏；
- 同一路径出现两次 → 后者覆盖前者，并产生一条 `warning`；
- 未闭合的 `<file>` 在流结束时以"已收到的内容"收尾，`file_end` 带 `truncated:true` 并产生 `warning`（宁可产出半成品，也不丢整轮）；是否重发由编排层的修复轮决定（§2.2）。

### 1.3 解析状态机

```
        ┌────────┐  <plan>   ┌──────┐  </plan>  ┌────────┐
        │ OUTSIDE│──────────▶│ PLAN │──────────▶│ OUTSIDE│
        └────────┘           └──────┘           └────────┘
             │ <file path>                ▲
             ▼                            │ </file>
        ┌────────┐  任意字符（累积/流式发送）│
        │  FILE  │─────────────────────────┘
        └────────┘
```

实现要点（`server/agent/protocol.ts`）：

- 维护 `buffer: string`，每次 `push(chunk)` 后循环匹配"下一个标签"；
- 只处理**已完整到达**的标签（`<plan>`、`</plan>`、`<file path="...">`、`</file>`、`<delete .../>`），半截标签留在 buffer；
- OUTSIDE 状态下的普通文本累积为 note，`<` 开头但不能构成标签的字符退化为文本（容忍模型写出 `a < b`）；
- 每次 push 返回 `AgentEvent[]`，不抛异常——解析器永远不因为模型犯错而中断流。

### 1.4 事件模型（前后端共用）

```ts
type AgentEvent =
  | { type:'stage'; stage:'plan'|'write'|'verify'; status:'running'|'done' }
  | { type:'note'; text:string }
  | { type:'notice'; level:'info'|'warn'; message:string }   // 排队/换家/修复轮的过程提示：非错误、不进版本历史
  | { type:'plan'; plan:Plan }
  | { type:'file_start'; path:string }
  | { type:'file_delta'; path:string; chunk:string }
  | { type:'file_end'; path:string; lines:number; content:string; truncated?:boolean }
  | { type:'delete'; path:string }
  | { type:'check'; check:Check }
  | { type:'warning'; message:string }
  | { type:'done'; version:number; usage:Usage; provider?:ProviderInfo; partial?:boolean; kept?:number }
  | { type:'error'; code:ApiErrorCode; message:string }
```

`file_end.truncated` 由解析器在闭合标签没等到时置真——它把"内容不可信"这件事从隐式约定变成显式字段，中断保留（§2.5）和修复轮（§2.2）都靠它区分新旧内容。`done.usage` 跨修复轮累计，`done.provider` 回显这次实际打成的一家模型。

**这是整个系统的主动脉**：SSE 传输的是它，前端 reducer 消费的是它，测试断言的也是它。

## 2. Agent 编排（runner + 编排层）

编排分两层：`runner.ts` 的 `runGeneration` 负责**单次** plan → write → verify；`server/index.ts` 负责**链级**决策——排队、故障转移、修复轮、失败判定与落库。

```
handleGenerate(project, prompt, provider?)            —— server/index.ts
  ├─ resolveChain(catalog, 访客设置) → 解析链；空链 → 412 provider_unavailable
  ├─ for 链上每一家（attemptWith）：
  │     ├─ queue.waitForSlot（免 Key 通道 30s 一档；等不到 → 换下一家）
  │     ├─ runGeneration(ctx, new ModelEngine(provider), sink)   —— runner.ts
  │     │     ├─ stage(plan, running) ──► placeholderPlan → plan 事件
  │     │     ├─ stage(write, running)
  │     │     │     for await (chunk of engine.write(ctx))
  │     │     │         parser.push(chunk) → 转发事件（模型自己的 plan 会覆盖占位方案）
  │     │     ├─ verify：assemble(files) → check / missing / truncated / broken
  │     │     ├─ 若无任何文件 → error(protocol_error)
  │     │     └─ done(version, usage, provider)
  │     └─ 失败且 canFailover（本轮无任何产出）→ notice(warn)「换下一家」→ 下一家
  ├─ 修复轮循环（≤ NUCLEUS_MAX_REPAIR_PASSES=2）：missing/truncated/broken → repairMessages 只重发这些文件
  ├─ 修完仍有问题 → notice(warn) + 保留当前最好的产物（不判整次失败）
  └─ 持久化：files / plan / checks / version++ / message / usage（跨轮累计）/ provider 落库
```

**引擎接口**（现在只有一个实现）：

```ts
interface AgentEngine {
  id: ProviderId                                     // 这次打给谁：'pollinations' | 'deepseek' | 'custom' …
  info: ProviderInfo                                 // id/label/model/free，done 事件与落库用它
  plan(ctx: GenContext): Promise<Plan>
  write(ctx: GenContext): AsyncIterable<string>      // 原始协议文本增量
}
```

`ModelEngine` 是唯一的 `AgentEngine` 实现：`write()` 把上游 SSE 的 delta 原样 yield；`plan()` 返回 `placeholderPlan(prompt)`——从需求文本里捞引号内的应用名，**不调模型**，纯粹让用户在首字节之前就看到"它在做什么"。打不到真实模型就没有第二条产出路径：解析链为空直接 412，不存在"退回到某条不花 token 的路"。第二条路曾经存在过（写死配方的 mock 生成链路），删掉它的理由见 [03 §2](03-技术架构文档.md)——它让"没配 Key 也能生成"变成假的。

### 2.1 上下文构建（`prompts.ts`）

首轮：

```
[system]  你是 Nucleus 的应用生成引擎 ……（协议说明 + 工程约束 + 设计系统）
[user]    需求：{prompt}
```

迭代轮：

```
[system]  同上
[user]    当前项目文件（manifest + 相关文件正文）：
          <manifest>
          index.html（完整，3204 字符）
          styles.css（完整，2810 字符）
          app.js（未提供内容：上下文预算已满，4120 字符）
          </manifest>
          <file path="index.html">…</file>…
          用户的新要求：{prompt}
          只输出发生变化的文件；未变化的文件不要重复输出。
```

**上下文选择策略**（`selectContext`，详见 [08 §5.4](08-完整技术文档.md)）：

1. **打分**：`语义类别亲和度（分路径权重）+ 词法命中 + 入口文件保底分`；
   「把主色换成墨绿」→ styles.css +8 · index.html +3；「加一个筛选按钮」→ app.js +8；
2. **选取**：按分数降序（同分按体积升序），放得下就完整放，放不下就**截断**而不是丢弃；
3. **manifest**：列出全部文件及其状态（完整 / 已截断 / 未提供），让模型知道项目里还有什么。

> 旧策略是"按路径顺序累加，超预算整份丢弃"——模型会以为那个文件不存在，从而把它整个重建。
> 新策略把"没给全"和"没有这个文件"这两件事彻底分开。

约束（写进 system prompt，且被测试断言）：

- 单文件 ≤ 400 行，总文件数 ≤ 5；
- 只用原生 HTML/CSS/JS，不引入构建步骤；需要库时只允许 CDN `<script>`，且页面里做降级；
- 必须有 `index.html`；CSS/JS 用相对路径引用；
- 移动端可用（≤ 560px 单列、按钮全宽，不允许横向滚动）；
- 真实数据与真实交互，禁止 Lorem ipsum 占位；
- 设计系统：8pt 间距、圆角 12–16px、字体栈、主色由用户偏好注入；
- **设计令牌契约**（本轮新增，决定"实时微调"能不能用）：主色必须写成 `--accent`、圆角必须写成 `--radius`、都定义在 `:root` 上，其余位置一律 `var()`，并派生 `--accent-soft`（focus 光环/选中态的浅底）与 `--accent-ink`（主色上的文字色）。把颜色散写在各个规则里，用户的"换个主色"就只会改到一半。

**修复轮上下文**（`repairMessages`）：assemble 判定需要重发时，提示词只列出**要重发的文件与各自的具体原因**（"页面引用了它但上次没有输出 / 上次写到一半就断了 / 上次输出的内容语法不通"），明确禁止重写其他文件（否则已做好的部分会被换个写法全文覆盖，版本历史变成毫无意义的一次替换），并要求与已有文件的 DOM id / class / 全局变量严格对应。

### 2.2 真实模型的漂移如何被收敛

模型一定会犯错。第一道仍是流式解析层的"最小干预"漂移纠正（在 `protocol.ts` 解析时做，只在格式层改字符，不改语义）：

| 漂移 | 修正 |
| --- | --- |
| 用 ```` ```html ```` 包裹整个 `<file>` 内容 | `file_end` 时剥围栏 |
| 写成 `<file name="a.html">` | 属性名兼容 `name` / `filename` |
| 大小写 `<FILE PATH=...>` | 标签名与属性名转小写后匹配 |
| 忘记闭合 `</file>` 直接开下一个 `<file>` | 解析器见新 `<file>` 时先收尾上一个 + warning |
| 输出 `<!DOCTYPE html>` 前有元话语 | OUTSIDE 状态自动归入 note |

但真正会"毁掉一次生成"的失败形态不在标签层，而在**这一家不行、这一轮没写完**。它们由四层机制收敛，各司其职：

| 失败形态 | 收敛机制 | 落点 |
| --- | --- | --- |
| 免 Key 通道配额（实测同一 IP 每 30 秒 1 次） | 按提供方 `minIntervalMs` 的 FIFO 闸门把并发压成串行；预计等待超过 `NUCLEUS_MAX_QUEUE_WAIT`（默认 90 秒）抛 `QueueFullError` 换下一家——**被拒的请求不推进 nextAt，不把后面的人一起推后**；等待超过 1 秒先发 `notice(info)` | `queue.ts` / `server/index.ts` |
| 某一家鉴权失败 / 限流 / 超时 / 网络 / 不按协议出码 | 故障转移 `canFailover`：错误码 ∈ {llm_auth, llm_quota, llm_timeout, llm_network, protocol_error} **且本轮尚无任何产出**（raw 为空且无已完成文件）。已经吐了一半绝不换家——两份代码互相覆盖比直接失败更糟。换家发 `notice(warn)`；只有终态失败才发 `error` | `runner.ts` / `server/index.ts` |
| 输出预算截断（思考链吃光正文） | `max_tokens` 必须由目录显式给（不传时上游默认 1500 completion tokens，四文件应用会被从中间截断）；gpt-oss 这类思考模型固定 `reasoning_effort: low`（它只支持 high/medium/low，minimal 会 400）；429 的 `Retry-After` 解析成 `retryAfterMs` | `providers.ts` / `llm.ts` |
| "自检全绿但一打开就白屏" | 语法闸门 `scriptSyntax()`：`new Function` **只编译不执行**，每个 `.js` 一条 block 级 check；assemble 报出 `missing` / `truncated` / `broken` → 修复轮（repair pass）循环 ≤ `NUCLEUS_MAX_REPAIR_PASSES`=2 轮，`repairMessages` 只重发这些文件并带上具体原因（同一路径的多条原因按 path 去重合并）；修不动 → 保留当前最好的产物 + 一条 `notice(warn)`，**不把整次生成判成失败** | `assemble.ts` / `prompts.ts` / `server/index.ts` |

不做的事：不改写代码内容、不猜测缺失文件的内容、换家时不覆盖已有产出。**纠正只发生在格式层与"再问一次"层。**

### 2.3 一次请求的完整时序：四个环节如何落在同一条事件流上

这是整个设计里我最想让人看懂的一段。下表是**一次真实的生成请求**从发起到落盘的完整事件序列，右侧标注它服务于 Atoms 的哪个环节：

| # | 事件 | 发生了什么 | 对应环节 |
| --- | --- | --- | --- |
| 0 | （可选）`notice(info)` | 免 Key 通道正在排队："前面还有约 N 秒"——等待超过 1 秒就先发，不让人对着转圈猜 | ② 过程可见 |
| 1 | `stage(plan, running)` | 阶段药丸切到「拆解需求」 | ② |
| 2 | `note` | Agent 的一句话口播（名字 + 简介） | ② |
| 3 | `plan` | **方案卡落屏**（来自占位方案，模型自己的 plan 会在流里覆盖它） | ① 任务简报 |
| 4 | `stage(write, running)` | 阶段药丸切到「编写代码」 | ② |
| 5 | `file_start(index.html)` | 文件流出现第一行，代码面板同步高亮该文件 | ② |
| 6 | `file_delta` × N | 内容逐字流式追加，前端按 rAF 批量 flush | ② |
| 7 | `file_end(index.html, lines)` | 该行打上完成勾，显示真实行数 | ② |
| 8 | `file_start/delta/end` × 其余文件 | 逐个文件重复 5–7 | ② |
| 9 | `stage(verify, running)` | 阶段药丸切到「静态自检」 | ② |
| 10 | `check` × N | 入口文件 / 引用完整性 / 结构 / 体积 / 外链 / 沙箱安全 / 设计令牌 / **每个 .js 一条语法**，渲染为徽章 | ② 验收 |
| 10.5 | （可选）`notice(warn)` + 一轮新的 `write/verify` | **修复轮（repair pass）**：有 missing/truncated/broken 时，`repairMessages` 只重发这些文件（≤2 轮），复用同一家模型、不重发方案卡 | ② 验收 |
| 11 | `done(version, usage, provider)` | 服务端一次性提交：files + version + messages + usage（跨轮累计）+ provider；前端重新拉项目并挂载预览 | ③ 结果可交互 |
| 12 | （`POST /rollback`） | 复制目标版本为**新版本**，历史不可变 | ④ 可回滚 |

中途某一家失败会多出 `notice(warn)`"这家不行，正在换下一家"；只有整条链都没有产出时，才在末尾发一条 `error`（不再是"先红一条再成功"）。

四条设计约束贯穿其中：

1. **任务简报必须早于代码**（事件 3 早于事件 5）。这不是 UI 顺序，是协议顺序——`plan` 标签在协议里就排在 `file` 之前，模型被强制先给简报。
2. **"能点"与"生成完成"同时发生**（事件 11）。预览不是"生成结束后再点一个按钮打开"，而是 `done` 事件之后立刻拉一次项目快照（同一份数据里同时带着新版本与对应的 `srcdoc`），用户在同一刻看到完成提示和可点的应用。代价是多一次 GET，本地环境 5ms 量级；收益是省掉一次用户操作。
3. **半成品不落盘**。生成过程中的文件只存在于前端 `live` 态；只有 `done` 才提交。因此"用户中途点停止"走的是 §2.5 的中断保留，而不是丢一半。
4. **可见的不完整 > 静默的完整**。修不动时保留能用的部分并明说（`notice(warn)`），而不是把整次生成判失败或假装一切正常——少一个文件的应用还能继续对话让它补，报错清空则什么都没剩下。

### 2.4 为什么不用多角色（Emma / Alex / Mike）

Atoms 的做法是让 LLM 依次以不同角色口吻输出，前端按角色前缀切分成多张活动卡片。这件事**看起来很贵，其实不贵**——真正的成本不在提示词，而在于：

| 若采用多角色 | 代价 |
| --- | --- |
| 三次独立 LLM 调用 | token 与延迟 ×3，且三段之间的上下文要自己传 |
| 角色间一致性 | Emma 定的需求与 Alex 写的代码可能对不上，需要额外的仲裁或校验 |
| 失败面 | 任一角色失败，整轮重来；用户看到的是"团队开了三次会还没交付" |
| 对本项目的额外收益 | **≈ 0**：四个环节在产品意义上都能保留，差别只是气泡的标题 |

所以本项目的选择是：**阶段化输出**（任务简报 → 编写 → 验收），UI 上仍是一个 Agent 身份，但三段的信息是**真实执行结果**而非角色扮演——方案卡里的文件清单与后续实际写入的文件一一对应，检查徽章来自真实的静态检查。

**如果要做多角色**，改动点被限制在两处，架构不动：

1. **提示词层**：在 `SYSTEM_PROMPT` 里加角色前缀与输出格式（`<pm>…</pm>` / `<code>…</code>`）；
2. **事件层**：在 `protocol.ts` 增加角色标签解析，把角色前缀映射为 `note` 事件的 `role` 字段，前端 `ChatStream` 按 `role` 渲染不同气泡。

真正的多 Agent 编排（每个角色独立上下文 + 消息总线 + 任务图）则落在**生成层接缝**上（[03 §7](03-技术架构文档.md)）：在提供方目录之上新增一个 `AgentEngine` 实现，把多个来源的事件聚合进同一条 `AgentEvent` 流即可，上层零改动。

### 2.5 中断保留：点「停止」时到底发生了什么

产品承诺是"点了停止，已经写完的文件别丢"。朴素做法是直接 abort 掉 HTTP 连接 —— 但那样客户端收不到任何回执，只能靠轮询版本号去猜，体验很脏。

本项目的做法是**把"停止"做成一次显式的控制请求**：

```
客户端                                服务端
──────                                ──────
点「停止」
POST /stop ───────────────────────▶  running.get(id).abort()
                                    ↓
                              上游流在下一个增量边界停下
                                    ↓
                              parser.end() 收尾：
                              未闭合的文件标 truncated
                                    ↓
                    partialFiles(sink, previous)：
                      completed 里的   → 新内容
                      写了一半的       → 回退到旧内容
                      本轮新开没写完的 → 丢弃
                      deleted 里的      → 保持删除
                                    ↓
              有变化 → commit(label "中断保留 · N 个文件有变化")
              无变化 → 不产生版本
                                    ↓
◀──────────────────────────────────  done(version, partial: true)
客户端刷新 → 预览里就是保留下来的那些文件
```

三个关键设计：

| 设计 | 为什么 |
| --- | --- |
| **连接不断开**，用独立请求喊停 | 客户端能拿到 `done{partial:true}` 的明确回执，不需要轮询 |
| **协议层区分"闭合"与"截断"**（`file_end.truncated`） | 只有正常闭合的文件才算"写完了"；被截断的要回退到旧版，否则会留下半个坏文件 |
| **客户端断开也提交** | 用户直接关页面时，已完成的部分照样落库，不丢数据 |

代价：协议事件多了一个可选字段，编排层多了一个 `completed` 集合。换来的是"停止"这个动作从**丢弃**变成了**可控的部分提交**。

## 3. 生成链路：提供方目录、闸门与出厂示例

生成只有一条真实链路，四段各有明确的落点、各自可单测：

```
需求 ──▶ ① 提供方目录：解析链 ──▶ ② 提示词契约 ──▶ ③ 流式生成（闸门+SSE 解析）──▶ ④ 组装自检
          (providers.ts)          (prompts.ts)      (queue.ts / llm.ts /           (assemble.ts)
           谁来做这一单？          必须输出什么？      protocol.ts / runner.ts)       不合格交给修复轮（§2.2）
```

### 3.1 提供方目录与解析链（`providers.ts`）

**7 条内置预设**：`pollinations`（免 Key，GPT-OSS 20B，model 别名 `openai-fast`，`maxTokens: 12000`，`reasoningEffort: low`，`minIntervalMs: 31000`）+ `deepseek` / `gemini` / `moonshot` / `zhipu` / `openrouter` / `siliconflow`（后 6 条需要 Key，全部是标准 OpenAI 兼容端点）。想接自家网关，在 `config/providers.json` 追加一条同形状记录即可，不必改代码。

Key 来源优先级：**环境变量**（每条预设声明自己的 `keyEnv`，如 `DEEPSEEK_API_KEY`）＞ **`data/providers.local.json`**（已 gitignore，可放 Key）＞ **`config/providers.json`**（可入库，只改目录结构——按 id 逐字段合并，改一个模型名不会顺手抹掉 Key 来源和配额说明）。另有通用内联预设：`NUCLEUS_LLM_BASE_URL` + `NUCLEUS_LLM_MODEL`（+ `NUCLEUS_LLM_API_KEY` / `NUCLEUS_LLM_FREE=1` / `NUCLEUS_LLM_LABEL` / `NUCLEUS_LLM_MAX_TOKENS` / `NUCLEUS_LLM_TEMPERATURE`）合成 id=`env` 的预设并自动成为主力。

主力选择：`NUCLEUS_PROVIDER` ＞ 内联 env ＞ 配置文件 `default` ＞ `pollinations`。

**解析链**（`resolveChain`，按尝试顺序）：

1. 访客在设置页自带 Key（id=`custom`，**只对他自己生效**）；
2. 请求点名的预设；
3. 服务端目录（主力提到最前）；
4. 免 Key 通道永远排在最后兜底。

未就绪（没 Key）的预设不进链；全链为空 → 412 `provider_unavailable`。**没有"退回模板"这条路。**

为什么做成"目录 + 解析链"而不是写死一个地址：免 Key 通道实测（2026-11-03）匿名档配额约**同一 IP 每 30 秒 1 次**请求，而服务端只有一个出口 IP——单点必然把访客挡在门外；有链才能排队 + 故障转移，并且你能用环境变量决定谁做主力。

### 3.2 配额闸门（`queue.ts`）

`waitForSlot(providerId, { minIntervalMs, maxWaitMs, signal })` 按提供方把并发压成 FIFO 串行：预计等待超过 `NUCLEUS_MAX_QUEUE_WAIT`（默认 90 秒）抛 `QueueFullError` 让编排层换下一家，**被拒的请求不推进 `nextAt`**——不排队就不该把后面的人一起推后。"判断等待时长"与"推进 nextAt"在同一个同步块完成，Node 单线程中间不 await 就不会有抢槽竞态。单进程内存态足够：持久化层也是单文件 JSON，同一约束（[03 §2](03-技术架构文档.md)）。

### 3.3 客户端与错误映射（`llm.ts`）

`streamChat` 只做三件事：发请求、把 SSE 解成文本增量、把失败映射成平台错误码。本轮的关键细节：

- `max_tokens` 必须由调用方显式给——上游不传时用自己的小默认值（Pollinations 实测 1500，含思考链，四文件应用必被截断）；
- `reasoning_effort` 透传给思考型模型（gpt-oss 只认 high/medium/low，minimal 直接 400）；
- 429 时解析 `Retry-After`（秒数与 HTTP 日期两种写法）为 `retryAfterMs`，上限 120 秒；
- 每个 `LlmError` 带 `retryable`：401/403/404 换一家也没用，429/5xx/网络/超时值得换家——**"能不能换一家"由这层判断，编排层不必认识 HTTP 状态码**；
- 首字节 30s / 空闲 60s 双超时，单个坏 SSE 帧只跳过不中断整条流。

### 3.4 协议解析与组装自检

NWF 协议（§1）与 `assemble` 自检（§4）构成"模型输出的收口"：解析器容错漂移、组装器产出 `checks / missing / truncated / broken`，其中的语法闸门是"结构全绿但打开白屏"这类静默缺陷的**唯一拦截点**。修复轮怎么消费这些信号见 §2.2。

### 3.5 出厂示例：链路真实性的固化快照

`server/store/factory-example.json`（入库）是一次**完整走真实链路**的产物记录：prompt / provider（id、label、model、free）/ usage（ms、chars、tokens）/ generatedAt / plan / files。当前示例「小账本」：3 文件、7719 字符、51.6 秒、6327 tokens，模型「免 Key · GPT-OSS 20B（openai-fast）」，且**含 1 轮修复**（app.js 第一次被截断）——示例本身就是修复轮在跑的证明。

- 用 `npm run make:factory` 重新生成：脚本走**产品自己的 HTTP 链路**（`createNucleusServer` + `/generate` SSE），排队 / 故障转移 / 修复轮 / 自检 / 落库全部生效——脚本不会测出一条产品里不存在的路径；产物有阻断级自检失败或缺引用时**拒绝写入**。
- `seedDatabase` 只在项目列表为空时载入它；**绝不在启动时调模型**：部署环境出不了网会把服务卡死在启动阶段，30 秒 1 次的免 Key 配额也不该被每次容器重建烧掉。
- schema 从 1 升到 2 时读到旧库会先备份（`db.json.v1-backup.<ts>`）再重建，顺带清掉上一版预置的 10 个 mock 项目——过期数据不进新契约。

## 4. 预览组装与沙箱（`preview/assemble.ts`）

### 4.1 组装算法

输入 `FileEntry[]`，输出 `AssembleResult { html, entry, checks, inlined, missing, broken }`：

1. 选入口：`index.html` → 否则按 `index|main|app` 前缀的第一个 `.html` → 否则失败（check `entry` = false）；
2. 内联 `CSS`：把 `<link rel="stylesheet" href="styles.css">` 替换为 `<style data-src="styles.css">…</style>`（保持原位置，保证层叠顺序）；
3. 内联 `JS`：把 `<script src="app.js"></script>` 替换为 `<script data-src="app.js">…</script>`（保持原位置，保证 `defer` 语义以外的基本顺序）；
4. 注入错误桥 + storage shim（在 `<head>` 之后的第一行，早于任何业务脚本）；
5. 若有设计微调，在 `</head>` **之前**插入 `<style data-nucleus="tweak">`（同优先级"后写者胜"，不需要 `!important`）；
6. 静态检查（含本轮新增的语法闸门）：

| check id | 规则 | 失败后果 |
| --- | --- | --- |
| `entry` | 存在入口 HTML | 预览不可用 |
| `refs` | 所有相对引用的文件都存在 | warning（预览留空占位；路径进 `missing`，驱动修复轮） |
| `structure` | 含 `<html` 与 `<body` | warning |
| `size` | 总字节 < 400KB | warning |
| `external` | 列出 CDN 外链（提示"离线不可用"） | info |
| `sandbox_safe` | 不含 `top.location` / `parent.document` 等越权访问 | warning |
| `theme_vars` | **必须声明 `--accent` 才算 ok**（实时改主色靠它）；只有 `--radius` 时如实提示"圆角可实时微调，主色需要重新生成" | info |
| `syntax:<path>` | 每个 `.js` 一条：`new Function` **只编译不执行**，抓"字符串没闭合"这类结构检查全绿、一打开就白屏的缺陷 | **block**（路径进 `broken`，驱动修复轮） |

### 4.2 错误桥

```js
// 注入到每个预览文档最前面
(function () {
  var post = function (level, msg) {
    try { parent.postMessage({ __nucleus: 1, level: level, message: String(msg) }, '*') } catch (e) {}
  };
  addEventListener('error', function (e) {
    post('error', (e.message || 'Error') + ' @' + (e.filename || '') + ':' + (e.lineno || 0));
  });
  addEventListener('unhandledrejection', function (e) {
    post('error', 'Unhandled rejection: ' + ((e.reason && e.reason.message) || e.reason));
  });
  var ce = console.error;
  console.error = function () { post('error', [].map.call(arguments, fmt).join(' ')); ce.apply(console, arguments) };
  // localStorage shim（不透明源下原生 storage 抛 SecurityError）
  try { localStorage.getItem('__t'); } catch (e) { /* define in-memory shim */ }
})();
```

父窗口只信任 `event.source === iframe.contentWindow` 的消息，且用 `__nucleus: 1` 打标，避免误收第三方消息。

### 4.4 设计微调：把确定性修改从模型手里拿回来

**问题**：用户说「主色换成玫红」，走生成链路要 1–2 秒、结果不可复现（同一个"玫红"每次色值都不同），还会产生一个只改了一行 CSS 的版本，把真正有意义的迭代历史稀释掉。

**做法**：把视觉参数从"语义修改"里切出来，做成一组确定的 CSS 变量覆盖。

```
面板(色卡/滑杆) ──┬─▶ postMessage {__nucleus_tweak:{reset,vars}} ──▶ 沙箱 documentElement（即时，不重载）
                  └─▶ PATCH /api/projects/:id {tweak}（防抖 400ms，持久化）
                                   └─▶ assemble(files, tweak) 注入 <style data-nucleus="tweak">
                                          └─▶ 刷新预览 / 分享页 / 导出 ZIP 三处一致
```

三个实现细节值得写下来：

1. **为什么是 postMessage 而不是重新组装 srcdoc**：srcdoc 一变，iframe 文档就重载，应用里填了一半的表单和列表状态全没了。"调个颜色"不该有这个代价。变量写到 `documentElement.style` 上，优先级高于 `:root` 规则，且只触发样式重算。
2. **一套派生规则，两处消费**：`shared/theme.ts` 里的 `lighten` / `contrastInk` / `tweakVars` 同时被服务端（注入 `<style>`）与前端（postMessage 推送）引用。如果各写一份，"调色时是 A、刷新后是 B"这种 bug 会非常难查——还要在预览 / 分享页 / 导出 ZIP 三个消费点之间保持一致。
3. **刷新后的自愈**：iframe 的 `onLoad` 会用当前草稿再推一次变量。这样"保存过程中刚好重载"这种竞态不会闪回旧配色。

**边界与取舍**：微调只覆盖 `--accent*` 与 `--radius`，其余视觉仍由生成结果决定。这也是提示词里「设计令牌契约」（§2.1）存在的原因——模型把颜色散写进各个规则时，实时微调就覆盖不到。`theme_vars` 检查已改严：必须声明 `--accent` 才算 ok；应用只有 `--radius` 时如实提示"圆角可实时微调，主色需要重新生成"——宁可承认覆盖不到，也不做一个看起来生效的假开关。

## 5. 持久化与版本（`store/`）

### 5.1 原子写

```ts
async function save(db) {
  const tmp = `${file}.${process.pid}.tmp`
  await writeFile(tmp, JSON.stringify(db))
  await rename(tmp, file)          // 同分区 rename 是原子的
}
```

- 单进程内用**串行写队列**（`this.queue = this.queue.then(doSave)`）避免并发写坏；
- 读走内存副本，写完成才更新内存 → 读到的永远是已落盘状态；
- schema 版本为 `2`：读到旧 schema 时**备份 + 重建**（`db.json` → `db.json.v1-backup.<ts>`，重建空库），不把携带旧 `engine` 字段的过期数据带进新契约；
- 空库时由 `seedDatabase` 载入**出厂示例**（§3.5，真实模型产物固化），不在启动时调模型。

### 5.2 版本

- `generate` / `rollback` 成功后：`version.seq = project.version + 1`，落一份**完整文件快照** + `changed[]`（与上一版比对得出的路径集合）；
- `rollback(seq)`：把目标版本的 `files` 复制成**新版本**（`label: "回滚至 v{n}"`），历史不删；
- 裁剪：超过 30 个版本时删 `seq` 最小的非 1 号版本。

### 5.3 一致性

生成过程中的文件**不落盘**，只有 `done` 时一次性提交（files + version + messages + usage + provider）。"用户中途停止"走 §2.5 的中断保留：只提交**正常闭合**的文件（写了一半的回退旧版、新开没写完的丢弃）；若没有任何完整变化则不产生版本——半成品不会污染当前版本（PRD §5.4）。

两条本轮补上的账：

- **usage 跨修复轮累计**：修复轮每跑一次，新 sink 的 `ms / chars / tokens` 与之前各轮相加后才进 `done`——只报最后一轮会让界面上的耗时与 token 比真实值小一大截。
- **失败判定必须先看了 `result.ok`**：一个真实踩过的坑——编排层曾用 `result.failed ?? 默认值` 判失败，而成功时 `failed` 是**显式 null**，`??` 把 null 当缺失，导致"生成成功、文件也落库了，但前端只看到红色报错"。现在失败判定第一步永远看 `result.ok`。

## 6. 前端状态机

```ts
type StudioState = {
  project: Project | null
  messages: Message[]
  versions: Version[]
  live: {                      // 流式中的临时态
    running: boolean
    stage: 'plan'|'write'|'verify'|null
    plan: Plan | null
    files: Record<string, { content: string; lines: number; done: boolean }>
    checks: Check[]
  }
  error: { code: string; message: string } | null
  tab: 'preview'|'code'|'versions'
  device: 'desktop'|'tablet'|'mobile'
}
```

- 单个 `useReducer`，action 即 `AgentEvent | 本地 UI action`；`notice` 事件渲染为过程提示（排队 / 换家 / 修复轮），与红色 `error` 区分，不进版本历史；
- `live.files` 与 `project.files` 分离：**流式期间预览显示 live，`done` 后以服务端返回的项目为准**（服务端是唯一真相）；
- 打字机节流：`file_delta` 累积到 buffer，`requestAnimationFrame` 批量 flush，避免每 chunk 一次 setState；
- `abort`：`AbortController` → 关闭 SSE → 丢弃 `live`，保留旧项目状态。

## 8. 错误处理矩阵（实现级）

| 层 | 失败点 | 处理 |
| --- | --- | --- |
| 编排 | 解析链为空（没有就绪的提供方） | 412 `provider_unavailable`，流根本不开始；**不存在退回模板的路径** |
| LLM | 401/403 | `llm_auth`（retryable=false）：访客自带 Key 填错时退回免 Key 通道比硬失败友好——本轮无产出则换家（`notice(warn)` 说明"这家不行"），有产出则终态报错 |
| LLM | 429 | `llm_quota`，`Retry-After` 解析为 `retryAfterMs`；多数 429 已被排队闸门挡在门外，闸门等不到（>90s）直接换下一家 |
| LLM | 30s 无首字节 / 60s 空闲 | `llm_timeout`，中止连接；本轮无产出 → 换家 |
| LLM | 流中断（无 `[DONE]`） | 已产出文件保留，未闭合的标 `truncated` → 修复轮重发（§2.2） |
| 协议 | 无任何 `<file>` | `protocol_error`，附原文开头便于诊断；本轮无产出 → 可换家，全部失败才终态报错 |
| 组装 | 无入口文件 | check 失败 + 预览占位，**不报错**（应用仍可导出/继续迭代） |
| 组装 | 脚本语法不通 / 被引用文件缺失 | block 级 check + 修复轮（≤2 轮）；修不动 → 保留最好的产物 + `notice(warn)`，不判整次失败 |
| 排队 | 预计等待超过 `NUCLEUS_MAX_QUEUE_WAIT` | `QueueFullError` → 换下一家；**不推进该提供方 `nextAt`**，后面排队的人不被推后 |
| 存储 | 写失败（磁盘满/权限） | 500 + 内存态不提交，UI 提示"未保存，请重试" |
| 网络 | 前端 SSE 断开 | 断线提示 + 「重新生成」，不清空已有内容；服务端继续跑完并落库 |
| 编排 | 已开始流式后仍抛异常 | 请求级 catch 补一帧 `error{internal}` + 打日志——以前静默 `res.end()`，表现为"事件流戛然而止、没有 done 也没有 error"，是最难查的一类故障 |
