> 项目：Nucleus Studio —— 一个可运行的 "Atoms Demo"
> 调研时间：2026-11

## 1. 任务理解：把一段招聘文案翻译成验收清单

原始要求（README.md）里有三句话是硬约束，其余是加分项：

| 原文                                                                                                                                                  | 我的解读                                                                                       | 验收方式                                          |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| 「实现一个可运行的网页应用，具备类似 Atoms 的能力与 UI 交互体验，即通过智能体驱动的方式完成代码（应用）生成，并将生成的应用以可视化网页形式进行展示」 | 必须有两块：① 自然语言 → 可运行应用；② 生成结果要真的跑起来（iframe 里能点、能输入、能存数据） | 打开链接，输入一句话，等到一次真实模型生成完成（免 Key 通道实测 41.6–51.6 秒，前面有人排队会更久），看到一个能交互的页面 |
| 「具备真实交互（而非纯静态展示）」「具备数据持久化（不限技术方案）」                                                                                  | 平台自身要有持久化（项目、版本、对话），不只是生成物里有 localStorage                          | 刷新页面、换浏览器、重新打开链接，项目还在        |
| 「至少一个延展或衍生能力」                                                                                                                            | 基础闭环之外的"第二层能力"                                                                     | 见 §5 机会点，我做了 4 个                         |
| 「无需注册功能」                                                                                                                                      | 不要做登录墙，打开即用                                                                         | 首次访问 0 点击即可开始                           |
| 「可测试的在线访问链接」「实际可用的功能，而不仅是概念验证」                                                                                          | 部署 + 真机可跑                                                                                | 线上链接 + 验收清单                               |

时间盒 6–8 小时。这个约束决定了取舍：**少做「平台感」，多做「闭环质量」**。一个能稳定生成、能改、能回滚、能带走的最小闭环，比十个半成品功能更有说服力。

## 2. Atoms 产品观察

直接读了官网（atoms.dev）与文档站（help.atoms.dev），下面只记与本次 Demo 有关的事实：

**产品定位**：从一句想法到可上线产品的 AI 团队，最终交付物是"能卖的产品"，不是"能跑的 demo"。

### 2.1 四个不可省略的环节

把 Atoms 的交互拆开看，它由四个环节构成，缺任何一个，产品就退化成"一个能生成代码的聊天框"：

| #   | 环节                                       | Atoms 的表现                                                                                                              | 我的对应设计                                                                                                         |
| --- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| ①   | **对话是入口，但背后是"任务简报"**         | 用户说"做一个落地页"，团队负责人不会立刻写代码，而是先把自然语言翻译成一份有版块、约束、质量规则的任务简报，再 @ 给工程师 | `<plan>` 事件 → 方案卡：应用名 / 一句话简介 / 技术栈 / 步骤清单 / 文件清单。它是**生成的前置产物**而不是事后总结     |
| ②   | **每一步工作都可见**                       | 每条回复附带活动卡片，展开能看到工具卡片："读取文件""编写代码""运行终端命令""检查渲染后的页面"                            | 阶段药丸（拆解需求 → 编写代码 → 静态自检）+ 逐文件流式写入（真实路径、真实行数）+ 检查徽章。信息是真的，不是拟态标签 |
| ③   | **生成结果是一个可交互版本，不是一段代码** | 版本卡片出现后，点 Preview 直接在应用预览中打开，测试、迭代，而不是跳转到代码编辑器                                       | 沙箱 iframe 里真实可点，三档视口；应用内报错实时浮条回传宿主                                                         |
| ④   | **追加修改是增量，并且可回滚**             | 说"主题改成绿色"即可，Agent 在现有内容上应用修改并交付下一个版本；每条消息支持还原到该消息之前的状态                      | 只重写**变化的文件**；版本为不可变快照；**回滚本身也生成新版本**，历史永不丢                                         |

**这条拆解是我后面所有取舍的判据**：任何设计决策，只要它让这四个环节中某一个"看起来有"而不是"真的有"，就被否掉。

> 例：业界常见的做法是在生成完成后弹一张"生成成功"的卡片——这只满足了③的一半，因为产物还不能立刻试。本项目把预览挂载放在生成结束的**同一次事件提交**里，让"能点"和"生成完成"同时发生。

### 2.2 机制观察

1. **多智能体角色化编排**：Iris（研究员）/ Emma（产品经理）/ Bob（架构师）/ Alex（工程师）/ Sarah（SEO）/ Adrian（投放）…… 每个角色有明确职责边界，Mike 作为 Team Leader 负责串起来并"向你请求批准"。
   → 启发：Agent 的**过程可见**本身就是产品的一部分。用户不信任一个黑箱。
   → 我的取舍：**不复制多角色多调用**（成本与延迟翻倍、还要做角色间上下文传递），改用**阶段化输出**——任务简报（Emma 的职责）→ 编写（Alex 的职责）→ 验收（Mike 的职责）。四个环节在产品意义上完全保留，但只花一次模型调用（外加至多 2 轮"只重发问题文件"的定向修复）。详见 04 §2.4。
2. **Race Mode**：同一个 prompt 并行跑多个模型，直接对比取最优。
   → 启发：并排对比是刚需，但成本高。我改成更便宜的同构能力：**设置页可切换模型通道与模型**（预设目录 + 自带 Key，最小版）+ **同一项目保留每次生成的版本，可对比、可回滚**。
3. **Atoms Cloud + Publish/Share + Export/GitHub**：生成物不是终点，`Publish` 出稳定链接、`Share` 给协作者、`Export` 拿代码走。
   → 启发：**产物必须可带走**。这是我决定加"导出 ZIP + 只读分享页"的原因。

**额度模型**：Free 15 credits/天、Pro 100 credits/月、Max 500 credits/月 —— 按生成次数计费。这解释了为什么所有同类产品都在优化"一次生成成功率"：每次失败都是实打实的成本。

**Atoms 没做（或做得浅）的地方，就是我的机会点**

- 生成过程只给一句"正在生成"，出错后只能重新描述，**运行时错误不会被回灌给模型**；
- 版本可回退但**对比粒度粗**（看不到"这次改了哪几个文件"）；
- 分享出去的是产物，**不是可继续编辑的工作区**。

## 4. 关键约束与我的应对

这是本项目的核心决策，必须写在最前面：

> **手上没有任何可用的模型 Key**（平台云服务配额不可用，本地也没有 API Key）。
> 但公网存在一个**免 Key 的 OpenAI 兼容端点** `https://text.pollinations.ai/openai`（2026-11-03 实测：免 Key 可用，支持 SSE 流式与 `max_tokens`）。
> 于是约束从"能不能调到大模型"变成"**零配置也必须真实调用大模型，配额与延迟的代价由产品自己扛**"。

三条可选路线：

| 路线                                                                              | 结果                       | 判断                 |
| --------------------------------------------------------------------------------- | -------------------------- | -------------------- |
| A. 只做真实模型，要求使用者自己填 Key                                             | 打开即被拦，需要先配置     | ❌ 违反"可测试/可用" |
| B. 假装调了模型，返回写死的页面                                                   | 欺骗性 Demo                | ❌ 不可接受          |
| C. **必须真实调用外部模型 + 免 Key 通道永远兜底 + 预设目录可切换** | 零配置也打到真模型；给 Key 即换主力 | ✅ 选它        |

**上一版走的是"没 Key 时由服务端自己拼出一个应用"的模板兜底，本轮把它整体删掉了**（连同它的单测与运行时分支）。
理由不是它质量差，而是它让"**打开就能用**"变成假的：它只覆盖有限的几类应用，超出范围照样吐一个像样的东西，
静态自检全绿、预览能点，但用户拿到的不是自己说的那个需求——而这恰恰是本项目要交付的能力本身。
删掉之后契约层收敛成一套提供方语义：项目记录 `provider` + 给人看的 `providerLabel`，用量记录 `provider`，
没有就绪通道时报 `provider_unavailable`；数据库 schema 1 → 2，读到旧库先备份成 `db.json.v1-backup.<ts>`
再重建并载入出厂示例（顺带清掉了原先留在库里的 10 个模板项目）。**没有可用通道就是一条 412，不再退回任何模板。**

C 的具体形态：

- 平台内部定义 **统一的生成协议**（见 04 文档），模型只负责产出协议文本；实现只剩一条：**OpenAI 兼容 `/chat/completions` 的 SSE 流式，必须打到真实模型**；
- **模型通道目录** `server/agent/providers.ts`：1 条免 Key（`pollinations` · GPT-OSS 20B）+ 8 条需要 Key 的常用 OpenAI 兼容预设（DeepSeek / Gemini / Kimi / 智谱 / OpenRouter / 硅基流动 / 阿里云百炼 / 小红书 Dots）。想接自家网关不必改代码：在 `config/providers.json` 追加一条同形状预设，或用 `NUCLEUS_LLM_BASE_URL` + `NUCLEUS_LLM_MODEL`（配 `NUCLEUS_LLM_API_KEY`，免 Key 网关则 `NUCLEUS_LLM_FREE=1`）合成 id=`env` 的内联通道并自动成为主力；
- **Key 来源优先级**：环境变量（每条预设声明自己的 `keyEnv`，如 `DEEPSEEK_API_KEY`）> `data/providers.local.json`（已 gitignore，可以放 Key）> `config/providers.json`（可入库，只调整目录结构、不放 Key）；
- **解析链**（按尝试顺序）：① 访客在 `/settings` 自带 Key（id=`custom`，只对他自己生效）② 点名的预设 ③ 服务端目录（主力在前）④ 免 Key 通道永远兜底。没配 Key 的预设不进链；主力顺序是 `NUCLEUS_PROVIDER` > 配置文件 `default` > 内联 `env` > `pollinations`；全链为空才失败；
- **免 Key 通道的三条实测约束，由三层机制扛**：匿名档配额约"同一 IP 每 30 秒 1 次" → 新增 `server/agent/queue.ts`，按 `minIntervalMs`（31000）做 FIFO 闸门把并发压成串行，预计等待超过 `NUCLEUS_MAX_QUEUE_WAIT`（默认 90 秒）就抛队列满、换下一家，等待超过 1 秒先发一条 notice 告知"前面在排队"；不传 `max_tokens` 时上游默认只给 1500 个 completion token（含思考链），一个四文件应用会被从中间截断 → 预设固定 `maxTokens: 12000`；gpt-oss 是思考型模型，`reasoning_effort` 只接受 high/medium/low（传 `minimal` 直接 400），默认强度下正文常写不完 → 预设固定 `low`；
- **故障转移**：错误码属于 `llm_auth` / `llm_quota` / `llm_timeout` / `llm_network` / `protocol_error` **且本轮还没有任何产出**时才换下一家；已经吐了一半绝不换家（避免两份代码互相覆盖）。换家发 `notice(warn)`，只有终态失败才发 `error`；
- **零配置的产物也必须是真的**：首页示例「小账本」由 `scripts/make-factory.ts` 现场调用真实模型产出并入库（`server/store/factory-example.json`）——3 个文件 / 7719 字符 / 51.6 秒 / 6327 tokens，模型「免 Key · GPT-OSS 20B」，含 1 轮修复（`app.js` 第一次被截断）。`seedDatabase` 只在项目列表为空时载入它，**启动时不调模型**，否则部署环境出不了网会把服务卡死在启动。

这个取舍写进了 UI：项目徽章显示**这一次实际打到的通道**（`providerLabel`），排队与换家以 `notice` 实时上屏，首页 hero 明示"代码由真实大模型生成，默认走免 Key 通道，无需注册"。**不静默降级，也不假装**——现在也不存在可以悄悄退回的第二条产出路径。

## 6. 机会点（差异化设计）

1. **过程可见（Agent Trace）**：Plan / Write / Verify 三个阶段实时上屏，每个文件逐字流式产出。用户看到的是"一个工程师在干活"，不是一个 loading。
2. **运行时自愈（Self-Heal）**：预览 iframe 里的 `error` / `unhandledrejection` / `console.error` 通过 `postMessage` 回传，聚合成一个"检测到 N 个错误"的浮条，一键把**错误栈 + 出错文件**回灌给 Agent 修复。这是同类产品普遍缺失的一环。
3. **版本快照 + 回滚 + 文件级 diff**：每次生成落一个版本，时间线可回滚，diff 精确到文件。
4. **产物可带走**：ZIP 导出（零依赖自研打包）+ 只读分享页 `/p/:slug`（任何人打开就是可运行的应用）。
5. **确定性修改不排队等模型**：Atoms 的 Visual Editor 解决的是"已经生成出来了，还要调外观"。我做了它的最小可信版：主色 / 圆角**直接改变量**、毫秒生效、不重载页面、随分享与导出持久化。判断依据是——生成是概率的，但"换个颜色"不是概率问题。

## 7. 非目标（明确不做）

| 不做                                        | 原因                                                                                                                                      |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| 用户注册登录                                | 硬要求里写了"无需注册"                                                                                                                    |
| 真实部署生成物到独立域名                    | 沙箱与配额不可控，收益低（分享页已覆盖 80% 需求）                                                                                         |
| 并行跑多个模型的 Race Mode（完整版）        | 需要多倍 token 与结果仲裁逻辑；已用**最小版**替代：设置页可切换模型通道与模型名，版本时间线提供同一需求的多结果对比                             |
| 多角色 Agent（Emma/Alex/Mike 三次独立调用） | 一次 LLM 调用切成三角色只是文案，成本/延迟/一致性都不变；用**阶段化输出**替代，升级路径见 04 §2.4                                         |
| 完整视觉编辑器（拖拽布局 / 元素级编辑）     | 6-8h 内做不出可用质量。只做**令牌级**微调（主色 / 圆角）：它覆盖最高频的真实诉求，且不需要理解 DOM 结构，因此能保证"一定生效、一定能回退" |
| 移动端 App / 小程序                         | 与网页 Demo 定位不符                                                                                                                      |
